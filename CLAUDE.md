This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```sh
npm install
npm start                        # esbuild-bundles the renderer, then launches Electron
npm test                         # all unit tests (node:test over test/*.test.js and test/*.test.mjs only; work/compat holds old copies of the repo)
node --test test/plan.test.js    # a single test file
npm run bundle                   # renderer/app.js -> renderer/bundle.js (generated, gitignored)
npm run test:logging             # end-to-end check that renderer events reach the log file
npm run test:compat              # this build against a v0.8.0 copy in both directions (film, republish, glare); `-- --tag=v0.7.1` for another release (needs the tag locally; every check runs on 0.7.1 too); `-- --host=new --runs=5` repeats one direction and prints a pass count. `scripts/old-tree.js` prepares the copy in async steps with time limits, the old patch script under ELECTRON_RUN_AS_NODE=1 (without it electron.exe started as an app, never exited and held work/compat/<tag>)
npm run status                   # work/status/index.html: milestone cards, checks waiting on you, bugs, commits; rebuilt on every commit, `-- --watch` on every docs/ or todo.md edit
npm run bench                    # A/V sync + audio/video benchmark, film and share, 3 runs each (~15 min); writes work/bench/<version>-<date>.json
npm run dist:win                 # NSIS installer in dist/
npm run dist:mac                 # .dmg in dist/, only works on macOS (CI builds both, see .github/workflows/build.yml)
```

- `renderer/bundle.js` is what the window loads. Re-run `npm run bundle` after editing anything in `renderer/` or `shared/`.
- VS Code terminals set `ELECTRON_RUN_AS_NODE=1`, which makes Electron run as plain Node so `require('electron')` fails. `npm start` goes through `scripts/electron.js`, which removes it; run Electron directly (`electron .`) and you have to unset it yourself.

## Architecture

A small-room watch-together app (up to eight people). There is no server: peers find each other through Trystero's public Nostr relays and then connect directly over WebRTC.

**Media path (host only):** file → ffmpeg (main process) → fragmented MP4 on stdout → renderer pulls chunks over IPC → MediaSource on the host's `<video>` → `video.captureStream()` → WebRTC → viewer's `<video>`. The viewer never has the file. Its picture and sound come through the WebRTC stream; text subtitles come separately as cues. Images are the exception (see **Pictures**).

**Pictures:** an image file isn't streamed. `media.readImage` returns its bytes (formats Chromium can't show are converted to PNG by ffmpeg, `imageConvertArgs`), and the host sends them over the `image` action with `{id, name, mime}` metadata, to everyone on open and to each peer that joins. The host's `state` carries `image: {id}`; viewers keep the last picture per sender (`session.images`) and show it once the ids match. Extensions, Chromium mime types and the 50 MB cap live in `shared/images.json`. While a picture shows, the controls stay visible (volume still sets reaction sounds) but `control` ignores play/seek/loop.

**Screen sharing:** the host can share a whole screen or a window instead of opening a file. The picker is our own (`renderer/screenshare.mjs` shapes `desktopCapturer`'s source list for the thumbnail grid; `openSharePicker`/`startShare` in `app.js`), not the OS one: the renderer lists sources over `screenshare:sources`, the user picks one, `screenshare:select` tells `main/main.js` which id to trust (and whether system-audio loopback was requested), and only then does `navigator.mediaDevices.getDisplayMedia` resolve through `session.defaultSession.setDisplayMediaRequestHandler` — main only ever grants an id it just listed and the renderer just selected. A share claims host exactly like opening a file (`startShare`, same `claimedAt`/`isNewerClaim` dance) and publishes through `publishShareStream`, a leaner sibling of `publishStream` since a share's tracks are never swapped mid-session the way the file pipeline's are; viewers watch it through the same WebRTC path a video uses. Sharing has no timeline: `state.screen: {id, name, audio}` plays the role `image: {id}` plays for pictures, and `control` already ignores play/seek/loop because nothing is loaded. **Several people can share at once.** Only the first share claims host (that is what stops a movie); while anyone else's share is showing (`othersSharing`), a new one runs *alongside* it (`session.screen.alongside`) without touching the host or the role. Every sharer announces its own share on the `share` action (`{id, name, audio}`, or `{id: null}` on stop; `cleanPeerShare`), and its stream carries `claimedAt: Number(id)`. Viewers never put a share on `<video id="remote-video">`: the share grid (`renderShares`, laid out by the pure `shareTiles`/`shareView`/`gridColumns` in `screenshare.mjs`) gives every share, your own first, a tile with its own `<video>`, and the host's share is also read from its state so an older build still shows. Each other person's tile mixes its sound through its own gain (the tile's mute button) into the app output (`routeTileAudio`); your own tile is silent. Tabs (All / You / names) or a click on a tile switch between all tiles and one full size. A movie, picture or YouTube video ends every share (`receiveState` stops an alongside share on any non-share, non-idle state); the host stopping its share leaves the others running. Never put a live `MediaStream` on `<video id="local-video">`: it is wired to the file pipeline's `loadedmetadata`/`ended` listeners. Stopping — the Stop button, or the track's own `ended` event when the OS/browser share UI ends it — unpublishes and returns to idle the same way; switching source, or changing the audio source in Settings, is stop then start again (`restartShare`); resolution and frame rate apply live instead, via `track.applyConstraints()` (`applyShareVideoConstraints`), since a capture track tolerates that without restarting. **Audio quality** (Settings' bitrate choice, up to 510kbps — Opus's own practical ceiling, matching `maxaveragebitrate` in `lib.mjs`'s `preferStereoOpus`) needs no explicit re-apply at all: `tuneSenders` already runs once a second for every host and just reads `shareSettings.audioBitrate` instead of the fixed `AUDIO_MAX_BITRATE` whenever `session.screen` is active, so a Settings change takes effect on its own within a second, same as the adaptive per-viewer video bitrate already does.

**Share priority** (Settings, `sharePriority` in `screenshare.mjs`: Balanced / Sharp text / Smooth motion) sets the share track's `contentHint` and the senders' `degradationPreference` in `tuneSenders` (files always `maintain-framerate`); Sharp text also skips the 1080p downscale (bitrate still adapts), and a change applies live.

**Share receivers have no 250ms delay floor:** `adaptShareBuffer` (`telemetry.mjs`) starts each sharer's `jitterBufferTarget` at 0 and steps 0 → 100 → 250ms only while that connection shows loss or jitter (freezes ignored, a still screen sends few frames), shrinking after 30s calm; `applyViewerBuffer(pc, peerId)` picks it for `isShareSender` peers, while films keep `session.buffer` (250-750ms) and the caption-delay math unchanged.

**Screen-share audio** defaults to `audioDeviceId: 'system'` on macOS and `'app'` on Windows (`DEFAULT_SHARE_AUDIO`; Windows settings saved before `'app'` existed there are moved over once, the `winAppAudio` marker). `'system'` is `audio: 'loopback'` in the display-media handler, requested only when Settings' audio source is "System audio", never unconditionally. Electron's own `Streams.audio` doc comment says this is Windows only — that's stale against the installed version; verified directly (a standalone probe script, not through the app) that Electron 44 captures it on macOS too via Chromium's CoreAudio Tap integration, live and labeled "System audio" even when the shared source is a single window. It is **whole-system** audio either way, not isolated to the shared app. Settings' audio-source picker (`renderer/screenshare.mjs`'s `audioInputs`, shaped from `enumerateDevices()`) covers isolating one app two ways: a specific input device captured with `getUserMedia`, merged into the share's stream (`captureShareAudio` in `app.js`) — a virtual device such as BlackHole routes one app's output into this as an input, on any platform — or the `'app'` option (macOS and Windows), which gets real per-app isolation from the OS's own API. With `'app'`, a whole-screen share falls back to system audio (`audioSource` in `startShare`), since there's no single app to scope to.

**Both `getDisplayMedia`'s and `getUserMedia`'s audio requests need `SHARE_AUDIO_CONSTRAINTS` (`channelCount: 2`, `echoCancellation`/`noiseSuppression`/`autoGainControl: false`), never a bare `audio: true`.** Verified directly: an unconstrained loopback request comes back `channelCount: 1` with all three processing flags on — Chromium's defaults are tuned for a voice call, not for sharing music or system audio, and silently downmix to mono and run voice DSP over it unless told otherwise. `captureShareAudio`'s native/`'app'` path doesn't need this — `native/mac-app-audio` already asks ScreenCaptureKit for 2 channels directly — but anything going through a browser `getUserMedia`/`getDisplayMedia` call does.

**Diagnosing "no audio" reports for a share**, in order: (1) `appaudio`/`screenshare` log events (`main/app-audio.js`, `app.js`) say whether capture started, whether any bytes ever arrived (`appaudio receiving`), and the exact signal name plus a `DiagnosticReports` pointer if the native helper crashed; (2) `sampleTrackAudioLevel`/`sampleAudioLevelFromNode` (`app.js`) tap a throwaway `AnalyserNode` onto the host's outgoing track right after publishing, and onto each incoming share track in `routeTileAudio`, logging the measured RMS (`screenshare audio-level` / `received-audio-level`) — this is the only check in the chain that answers "is this actually sound, not silence," independent of whether every other layer claims success. A non-zero level on the host but zero (or absent, if the event never fires because the stream never attached) on the viewer narrows it to WebRTC transport or the viewer's own output device, not capture.

**Actual achieved audio bitrate** (not the configured ceiling `tuneSenders` sets, the real thing `getStats()` measures) needed its own fields in `telemetry.mjs`'s `readStats`: `audioOnly` there only ever substitutes audio for the video-shaped `inbound`/`outbound`/`inboundRtp`/`outboundRtp` fields when there's no video at all, so a share (video and audio sent together) was invisible to it. `audioInboundRtp`/`audioOutboundRtp` are separate, always-populated counters alongside those, unconditionally — logged as `audioSentBitrateBps` (`telemetry host-sample`) and `audioReceivedBitrateBps` (`telemetry viewer-sample`) via the same `bitrateDelta` byte-counter-over-time math the video fields already use. Opus is VBR, so this can read well under the configured cap for quiet content — that's expected, not a bug by itself.

**The `'app'` audio option** runs `native/mac-app-audio` (`main/app-audio.js` spawns it, `renderer/app-audio.mjs` consumes it), a small Swift tool built from source by `scripts/build-mac-app-audio.js` (`prebundle`'s `--if-needed`, or `prepare-package.js`'s `beforePack` hook for a release build — the committed source is the review surface, not a vendored binary, unlike the kind of third-party native addon this avoided pulling in). It takes the CGWindowID from a `window:<id>:<n>` desktopCapturer source (`windowIdFromSource`; `startShare` never passes `'app'` for a whole-screen share), resolves that window's owning `SCRunningApplication` via ScreenCaptureKit, and streams that app's audio alone — the same capability Discord's own "Application Audio" option on macOS uses, confirmed by having Discord's public-facing docs describe it and matching it to ScreenCaptureKit's content-filter API, not by decompiling Discord. It writes raw interleaved Float32 PCM to stdout (one line of `ready` or `error: ...` on stderr first, so the main process knows whether it actually started), pulled with the same backpressure-by-polling pattern as media.js's ffmpeg sessions (`appaudio:start/pull/stop`), and turned back into a `MediaStreamTrackGenerator('audio')` track in the renderer the way `frames.mjs` does for video.

**On Windows the `'app'` option runs `native/win-app-audio`** (C++, built by `scripts/build-win-app-audio.js` with the MSVC tools vswhere finds, static CRT; same `--if-needed`/`beforePack` hooks, shipped through `build.win.extraResources`). It speaks the same stdout/stderr protocol as the Mac helper, so `main/app-audio.js` and `renderer/app-audio.mjs` are shared. On Windows a desktopCapturer window id is the HWND; the helper resolves its PID (a Store app's `ApplicationFrameHost.exe` frame is followed to the hosted app's process) and captures it with WASAPI process loopback, `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE`, so child processes (browser audio services, plugin hosts) are included and nothing else is — this is what stops Discord's voice from riding along on a window share. It refuses this app's own window (the target is its parent process), since that would echo everyone back. Process loopback only delivers packets while the app is rendering sound, so the helper fills gaps with wall-clock-paced silence (only after 100ms without a packet, so it never cuts into real sound, and at most 100ms at a time, so a stdout stall resyncs instead of bursting zeros). Errors after `ready` (the app quitting) go to stderr as `error: ...` and `main/app-audio.js` keeps the last one as the session's error. **Any change to `main.cpp` needs `node scripts/check-win-app-audio.js`** (plays two quiet tones; by hand only, it makes sound): it checks one window's tone comes through and another process's doesn't, real-time rate through silence and through sound starting mid-capture, and the closed-window and app-exit errors. A clean compile proves none of that. An app using ASIO or WASAPI exclusive mode (common in DAWs) bypasses the Windows audio engine, so neither this nor system loopback can hear it.

**Whole-app share (Windows):** a window share normally captures one HWND, so an app's other top-level windows (a DAW's plugin windows, dialogs) never show. **Every window share on Windows** (`APP_WINDOWS`) goes through `followAppWindows` instead of `screenshare:select`; the share picker's "Include the app's other windows" checkbox (`shareSettings.wholeApp`, on by default) decides whether the layout keeps all the app's windows or only the shared one (whose frames then pass through untouched). **Minimized windows can be shared:** Windows refuses to capture a minimized window ("Could not start video source", verified), so the shared window's capture starts only once the layout shows it, and until then (or whenever it's minimized mid-share) the worker sends a card, "<app> is minimized", at the last picture's size twice a second (`placeholderText`; the helper reports `minimized` and the program's name as `app`; `screenshare app-showing` logs the switches). The picker lists minimized windows too (`minimized: true`, the program's icon as the thumbnail, a "Minimized" label). "System audio" for a window share is its own `getDisplayMedia` of a screen with loopback (`appwindows:system-audio`) whose video is stopped at once (audio keeps flowing, verified), since the window itself may not be capturable yet. The rest of the flow: `main/app-windows.js` runs `native/win-app-windows` (C++, built by the same `scripts/build-win-app-audio.js`), which prints a JSON line on every layout change with the virtual desktop and every visible window of the app (its process tree, or owned by one of its windows), topmost first, with its HWND and visible frame (`DWMWA_EXTENDED_FRAME_BOUNDS`) in physical pixels. The helper is event-driven (WinEvent hooks on the app's own windows, rescans at most every 8ms, a 1s safety scan that also refreshes the process tree), so a dragged plugin window's position follows every move and a still desktop costs nothing. **Each of those windows is captured on its own** and drawn together in stacking order, with **no frame ever touching the page's main thread**: `renderer/app-share-track.mjs` only starts/stops captures (getDisplayMedia exists only there) and transfers each capture's `MediaStreamTrackProcessor` readable, the output generator's writable and every layout to `renderer/app-share-worker.mjs` (bundled separately to `renderer/app-share-worker.js` by `npm run bundle`; the CSP only allows workers from the app's own files). The worker sends a frame when a capture delivers one (at most at Settings' frame rate, `writer.desiredSize` for backpressure) instead of on a free-running timer, which beat against the capture rate (23fps, uneven, measured); with only the shared window showing and the crop exactly its frame, that window's frames go out untouched (`passed` in the `screenshare app-composite` log event, every 10s, next to `composed`/`composeMs`/`framesIn`). Crop changes are logged as `screenshare app-crop`, twice a second at most. The crop is exactly the shared window while every other window is inside it (`cropTarget`, so opening a plugin inside it doesn't resize the stream) and widens to the 16px grid only for what reaches outside. Measured with two 1700×1300/800×600 windows repainting at 64Hz: the page's main thread under 20ms per 8s, the worker ~0.8ms per drawn frame; what remains is Chromium's own per-window capture (`desktopCaptureThread` in the main process, a GPU→CPU copy per frame), the same cost any window share has.

A Windows Graphics Capture of one HWND shows that window's content even where another window covers it, so another app's window on top neither hides part of the share nor leaks into it (verified: a fully covered window still captures in full). Only the gaps between the app's windows are black, and windows on any monitor are included. desktopCapturer doesn't list owned tool windows (a VST's `Vst3PlugWindow` is one), so main grants `window:<hwnd>:0` through `appwindows:grant`, and only for an HWND that session's helper currently reports (`appWindows.reports`); captures go one at a time through the single pending-source slot. The pure parts are in `renderer/app-share.mjs`: `captureChanges` (a window gone keeps its capture for `KEEP_HIDDEN_MS`, since Ableton hides plugin windows while it's in the background), `cropTarget`/`settleCrop` (follows the shared window at once, growing and shrinking: a shrink delay read as lag when resizing the window), `outputSize` (pixel for pixel, scaled down only to Settings' resolution or `MAX_OUTPUT`, 4K). A still screen still sends a frame every 500ms (keepalive); Settings' resolution/frame rate apply live through `composite.setLimits`. The share ends when the shared window closes (the helper's error), not when one capture ends: a closed plugin window's capture just drops out (drawing a frame of an ended capture throws, so `compose` drops that window instead). `node scripts/electron.js scripts/check-app-share.js` checks real pixels (coloured windows on screen for a few seconds, no sound: covered parts present, other app absent, a plugin dragged out and back in grows then shrinks the crop, a window opened and one closed mid-share, minimized gives the card and restored the picture); run it after any change to the helper, the track or the worker. `WIN_APP_WINDOWS=<exe>` points it at another build while the app holds the usual file.

**Generated video tracks report no size.** `getSettings()` on a `MediaStreamTrackGenerator` has no width or height, so `tuneSenders` and `chooseSendQuality` treated every film (`frames.mjs`) and whole-app share as 1080p: a 4K film went out at 4K, and a 720p one was scaled too far on a weak link. Both generators set `generator.frameSize` from the frames they write, and `trackSize(track)` in `app.js` falls back to it.

**On Windows the share picker never calls `desktopCapturer.getSources`.** Measured: each call froze the main process (which also moves and repaints the window) for 450–700ms, screens alone ~600ms, and the open picker refreshes every 2s, so the whole window hung while it was open. `main/share-sources.js` runs `native/win-share-sources` (C++, same build script) while the picker keeps asking and stops it after 6s idle; it prints one JSON line per 2s with every screen and window and a JPEG thumbnail (PrintWindow `PW_RENDERFULLCONTENT`, WIC), titles via `InternalGetWindowText` and no thumbnail for a hung or minimized window, so a frozen app can't stall it. Ids are Chromium's own (`screen:<EnumDisplayDevices index of an active display>:0`, `window:<hwnd>:0`) and are granted to `getDisplayMedia` as plain `{id, name}` (verified for both). It leaves out tool windows and click-through overlays, which desktopCapturer lists. Measured with the picker's 2s refresh: longest main-process freeze 558ms → 12ms. Mac still uses desktopCapturer.

**`app/main-stall`** is logged whenever the main process's event loop runs more than 150ms late (at most once a second): the first thing to read in a stutter report.

**Above-normal priority in a room (Windows, `main/priority.js`).** While any window is in a room (`app:in-room`, the same switch as the machine sampler), every pid in `app.getAppMetrics()` (main, renderer, GPU, network/audio services) is set to `ABOVE_NORMAL` with `os.setPriority`, re-applied every 2s for new processes and resets, and put back to normal on leaving; logged as `app/priority`. ffmpeg and the native helpers stay normal (ffmpeg can use every core; the net probe staying normal keeps its pings a measure of machine contention). Found 2026-11-08: two 15-40s freezes of a film (ICE disconnected both ways, 57-90% loss at the viewer, the viewer's own side clean) each began within seconds of `node --test` suites starting on the host's PC, whose router pings (timed in user space by `win-net-probe`) went 1ms → 150-350ms. Bench film under 48 busy threads: 9 → 22 frames/s presented at the viewer, A/V 2.66s → 5ms, 321 kbps → 5.2 Mbps sent. Raising needs root on macOS/Linux, so it does nothing there. **When a report shows `np.gw` rising with loss on both directions, suspect the host's CPU before the network.**

**Nothing may run a requestAnimationFrame loop while idle.** `drawCaptions` used to reschedule itself every frame from startup, forever; that alone kept Chromium producing 60 frames a second with nothing changing, a quarter of a core in the main process idle, and made the window stutter when dragged. It now runs only while a track's cues are loaded (`startCaptions`). Check with a page profile (`Performance.getMetrics` and a wrapped `requestAnimationFrame` over CDP): idle on home is 0 rAF calls.

**Two more things in `native/mac-app-audio/main.swift` that only broke once real audio was actually flowing, and that a clean compile — or a test against a silent app — will not catch:**

- **`extractPCM`'s `AudioBufferList` allocation must be sized by querying `bufferListSizeNeededOut` first, never `MemoryLayout<AudioBufferList>.size`.** That struct has a flexible array member (`mNumberBuffers` then that many `AudioBuffer` entries); the fixed Swift size only covers one, so a first version of this crashed the instant real stereo (two-buffer, planar) audio arrived.
- **`SCStream` must be held in a variable that outlives the `do` block that creates it.** A `let stream = SCStream(...)` declared inside `do { ... }` goes out of scope — and ARC deallocates it, silently tearing down capture — the instant that block ends, right after `startCapture()` resolves and "ready" is printed. No crash, no error: every subsequent capture callback just never fires again, because there is no stream left to fire it. Fixed by declaring `var stream: SCStream?` before the `do` block and assigning into it on success.

Both were found the same way: testing against an app genuinely playing audio, not a silent one (the first via `main/app-audio.js`'s "exited with code null" — killed by a signal — in the diagnostic log; the second via a standalone instrumented copy that logged every step of `extractPCM` and the raw stream callback, which showed the callback firing in an equivalent top-level test script but never firing at all from the real file — the output of a `diff` in behavior that line-by-line code reading had missed twice). Both were confirmed fixed by capturing real, continuous, non-silent PCM from a live stream for several seconds with the actual compiled binary, not by compiling cleanly — this file has compiled cleanly through every one of these bugs. Any future change to this file needs that same real-audio test before it can be called done.

**A host with nothing to show** (just stopped a share, with no file, image or YouTube video either) is a state `stateIsIdle` (`protocol.mjs`) recognizes — distinct from a file that's still opening, which already has a `playlistId` by the time it claims host. `receiveState` runs the same recovery for this that `onPeerLeave` runs for a host that's actually gone (clear `hostId`/`remote`, detach the stream, `setRole('idle')`), instead of leaving every viewer stuck as `'viewer'` with a frozen last frame and no way to host next — the only way back out used to be leaving and rejoining the room. Any future kind of hosted content that can end up with nothing to show needs this same check, or it regresses the same way.

- `main/plan.js`: pure decisions, unit-tested. Pass video through vs. transcode to H.264, ffmpeg args, subtitle burn-in filter graphs, HDR tonemap. Change behaviour here, not in `media.js`.
- `main/media.js`: runs ffprobe/ffmpeg. Detects a working hardware encoder once (nvenc/qsv/amf/videotoolbox, else libx264). Sessions are pull-based: `pull()` drains stdout, and ffmpeg blocks when the renderer stops pulling.
- `renderer/player.mjs`: the MediaSource pipeline. Seeking inside the buffer is a plain `currentTime` set. Seeking outside it, or changing audio/subtitle track, restarts ffmpeg at that time and resets the SourceBuffer (`abort`, `changeType`, `remove`). Keeps about 45s buffered ahead. If Chromium fails to decode a passthrough stream, it retries once with `forceTranscode`.
- `renderer/app.js`: the room and sync layer. The host is authoritative. It broadcasts a `state` action once a second and on every media event. The viewer interpolates time from it and sends `command` actions (play/pause/seek/loop/audio/subtitle), which the host applies. Whoever opens a file claims host; when two claims collide, the newer `claimedAt` wins (`isNewerClaim`).
- **Subtitles are per person.** Text tracks are converted to WebVTT by ffmpeg (`subtitleExtractArgs`, `parseWebVtt` in `plan.js`, cached in `media.js`) and drawn over the video by each app (`renderer/subtitles.mjs`). Viewers fetch a track's cues from the host with the `cues` request action; a subtitle file a viewer loads is read from their own disk and never shared. The viewer delays captions by the measured jitter-buffer delay (`delayMs` from `inboundDelta`) because its picture trails the host's clock. Image subtitles (PGS/VobSub) are still burned in by the host, so they are shared; the renderer never asks `planSession` to burn in a text track.
- **Default languages** (`renderer/languages.mjs`, pure and unit-tested in `test/languages.test.mjs`; Settings → Languages): "My language", Dubbed/Original, subtitles When I need them/Always/Off, signs & songs on dubs, prefer SDH, remember changes. The host's settings pick the audio (`player.pickTracks`, called in `StreamPlayer.open` before ffmpeg starts) and any image subtitle to burn in; each person's settings pick their own text subtitles in `syncCaptionsToMedia`, matched to the audio actually playing, and picked again when it changes language unless chosen by hand (`captions.manual`). **No wire change:** viewers read languages from the host's labels (`describeLabel`), so `trackFlagLabel` in `plan.js` adds `commentary`/`SDH` to a label when only the disposition says so. A track's language is its tag (639-1, 639-2/B or /T, BCP 47), else its title (one language named, whole words), else a sidecar file name (`x.en.forced.srt`). Commentary and audio-description tracks are never picked. Memory (`trackMemory` in localStorage, 200 keys): the host's per folder (`folderOf`), a viewer's per `room:<code>`; it stores a track's signature (language, title, kind) or `{off: true}`, never a path. Picks are logged as `media/tracks` with reason codes.
- **Skip intro, Previous/Next, skip flash** (`main/intro.js`, `renderer/skip.mjs`, both pure and unit-tested in `test/intro.test.js`, `test/skip.test.mjs`): when the host opens a video, main looks for the intro (`media:intro`, one search at a time, logged `media/intro`): a chapter titled Intro/Opening/OP/Main Title (10-240s, first half), else the audio this episode shares with a neighbour in its folder (natural order: next, previous, then one further each way; 0.4-2.5x the duration, `comparableLength`, so a double episode such as `S02E12E13` is compared with its single neighbours; at most 2 compared). The shared audio is a Haitsma-Kalker fingerprint of the first 10 minutes (mono 4 kHz, 64ms frames, 33 bands 200-1800 Hz), aligned by voting on exact 16-bit half-hash matches and accepted as 15-180s of frames within Hamming 11, edges trimmed by density so the end never runs into the episode; it yields every 4ms so main never stalls. Results (both episodes of a match) are cached in `userData/intros.json` by path, size and mtime, so the next episode is instant. Measured on real shows: 3-5s per file, worst event-loop lag 29ms. The host sends `intro: {start, end}` in `state` (`cleanIntro`; an older copy ignores it), so every viewer gets the button; it shows from the start until 1.5s before the end, also while the controls are hidden, and S presses it. The ±10/30 skips flash "Skipped forward 1m 30s" (presses within 1.2s add up, `chainSkip`), a CSS animation with no timer. Previous restarts the item past 5s (or with nothing before it), else plays the one before (`previousItem` in `playlist.mjs`); Next plays the next playable item; Shift+P / Shift+N.
- **Keyboard shortcuts panel** (`renderer/shortcuts.mjs`, unit-tested in `test/shortcuts.test.mjs`): the keyboard button right of the flag in the controls, or `?`, opens `#shortcuts`, a list built from `shortcutGroups(platform)`. - **Benchmark** (`npm run bench`, `scripts/bench.js`, pure parts in `scripts/bench-lib.js` + `test/bench.test.js`): the number every change to the media path is judged by. Same harness as `check-network.js` (hidden-but-shown-off-screen Electron windows, disposable profiles, local discovery, real WebRTC), muted, with the output gain feeding only a tap that reaches the destination through a gain of zero, so nothing is audible. It generates a clip with ffmpeg (moving `testsrc2`, a black patch that turns white for 4 frames, a 1kHz beep starting at the same sample, a quiet bed tone at a different pitch per channel, 28 events at irregular gaps of 2-3.6s, FLAC in Matroska) and measures on the **viewer**: *video time* = `requestVideoFrameCallback`'s `expectedDisplayTime` of the first white frame; *audio time* = the first sample of each beep in an AudioWorklet (`scripts/bench-tap.js`) hung off `output` (after the volume, after `routeRemoteAudio`/`routeTileAudio`), turned into the page's clock with `getOutputTimestamp()` read within 300ms of the beep (the context's clock steps by 10-30ms when the audio service is late, so one line for the whole run is wrong). Concealment is `conc - sil` over a window that starts 10s after the picture does. - **Audio in sync with the picture (M1.5):** WebRTC's lip-sync lines the audio and video tracks up by their capture times, so **every track a viewer receives must be stamped on the page's `performance.now()` clock**: `frames.mjs` (film video) already does; `renderer/app-audio.mjs` (the per-app share audio) used to stamp `AudioData` from 0, which put the audio on a base ~the page's uptime away from the video, so lip-sync held the picture back by that amount (~90ms on a fresh page, seconds and rising later) or gave up (`s.av` read ~16000ms at 15s of uptime, with audio and video then playing unsynced). It now uses `createAudioStamper`: the first quantum at `performance.now()` minus the audio that arrived with it, then frame counting, re-anchored after a delivery gap over `GAP_MS` (the Mac helper sends nothing in silence) and nudged towards the clock by at most 2ms per arrival so the helper's clock drift is followed but pull jitter isn't. The Windows whole-app worker (`app-share-worker.mjs`) has its own `performance.now()` that counts from the worker's creation, so it stamps with `pageClockUs` (`performance.timeOrigin` difference, the page sends its origin with `start`; verified in Electron: raw worker reading 508ms vs the page's 3580ms). **Any new generated track needs the same base.** The second gap is the viewer's Web Audio output (`routeRemoteAudio`/`routeTileAudio`, `outputLatency` + `baseLatency`, ~40ms): lip-sync lines the tracks up where audio leaves the jitter buffer, so the sound reached the speakers that much after the picture (film +41-48ms). `applyViewerBuffer` therefore gives the **video receiver** `jitterBufferTarget = adapted buffer + audioPathMs(...)` (`videoTargetMs`) and the audio receiver the adapted buffer alone: one fixed offset added to one side, never the adaptation added twice. Measured: the video wait survives lip-sync (it does not pull the audio later to match). **Captions** use `viewerDelayMs`: a measured delay (the frame's `expectedDisplayTime - captureTime`, or the video jitter buffer's recent delay) already includes the wait; only the requested-buffer fallback has it added (`test/telemetry.test.mjs` walks frames through a cue's start and end for all three sources, with and without the wait). **Telemetry:** `viewer-sample` `s.off` is the estimated sound-late offset in ms (`soundLateMs`: audio jitter buffer + `out` + `base`, minus video jitter buffer + decode, same sign as the bench); it includes whatever lip-sync is holding, so it shows the −650ms share gap that `s.av` (the two tracks' `estimatedPlayoutTimestamp` difference, a capture-time comparison lip-sync has already aligned) read as 11-22ms. `s.av` stays for continuity but do not read a sync problem from it. The estimate is a few ms to ~20ms off the bench's measurement (it cannot see the device or Bluetooth latency).

  - **Edge round trip:** `main/live.js` pings its `/live` socket (answered `pong` by `setWebSocketAutoResponse`, so the Durable Object stays asleep) and times it on a monotonic clock; `setFast(true)` (main calls it on `app:in-room`) makes that every 2s instead of every 15s, with one ping outstanding at a time and the 10s dead-socket rule counted from the first unanswered ping. `edgeRtt()` is the last answer if it is under 6s old, and `main/machine.js` puts it on the machine reading as `er` (ms), so it appears on `machine-sample`, per computer, whether or not anyone is watching live; it needs the "Send telemetry for development" checkbox on (that is what opens the socket) and is absent otherwise. Pings are counted in the sender's `wireBytes`, so `npm run test:live-rate` includes them (3 peers on the host 1.46 kbps, worst viewer 1.07). Worker unchanged: the auto-response was already deployed with M1.1. On Cloudflare's free plan each ping is a fraction of a request (WebSocket messages count 20:1): about 1,800 an hour per person in a room.
  - **One-way delay per direction:** `sync.mjs` `hostToViewerMs`/`toHostClock`/`viewerToHostMs`, from the clock offset `updateClock` already measures (host clock = ours + offset). The viewer takes each `state`'s `sentAt` against its arrival (the worst since the last sample goes on `viewer-sample` as `ow.hv`); the viewer stamps its `telemetry` report with `at` = its time plus the offset, and the host's reading of how late that is goes on `host-sample` as `ow.vh`. The offset assumes both directions are equal, so **only a rise means anything** (a queue building in one direction moves that direction's number and not the other's); negative values near zero are logged as they are.
  - **Context events:** `audio/device` (`why: room|change`, `kind` builtin/wired/bluetooth/hdmi/virtual/unknown from the label by `classifyAudioDevice`, `label` of the real device behind "default", `outs`, `sr`, `base`/`out` latency ms; labels are empty until media permission, which gives `unknown`, never an error); `crash/render-process-gone`, `crash/child-process-gone` (GPU, utility; reason, exit code), `crash/unresponsive|responsive`, `window/state` (minimized, restored, shown, hidden, focused, blurred, maximized, fullscreen; main, from BrowserWindow events), `window/fullscreen` and `window/visibility` (renderer), `power/state` (suspend, resume, lock, unlock, ac, battery, shutdown; the line before sleep is flushed), `action/<play|pause|seek|loop|audio|subtitle|volume|mute>` (`via: host|viewer|remote`, `from` for a command the host received; volume is debounced to one line per drag), `settings/change` (share settings; a device id is only "device") and `settings/save` (zoom, telemetry, "name changed"), `network/peer-state` now carries `change: {on, from, to}` and `network/ice-restart {connection, reason: transport|config-change|reconnect}`.   - **The report:** `npm run diagnostics -- --report` lists each mark (merged by id across logs, timed by the presser's clock, last note wins) with the viewer/host numbers from 5s either side of it and the context lines within 10s, and each viewer gets `Edge RTT`, `One-way delay` and **`Likely bottleneck`** lines. `scripts/bottleneck.js` compares troubled samples (loss over 2%, a freeze, the encoder held back by bandwidth or CPU) with calm ones: a link full of our video makes **its own** edge RTT climb by 40 ms and 1.5x while the other person's stays flat, which names that host's upload or that viewer's network; an encoder held back by CPU, slow encodes or long renderer tasks (a rate: 100 ms per troubled sample, so one stray task in a long session is nothing) is the host's computer, and slow decodes or long tasks the viewer's, but only while **neither** link is full (a computer is never blamed while the other side's link is full); both links up, neither up, or no `er` at all is `unclear` with the reason. `--live` prints a mark as `>>> MARK by <who> "<note>" <<<` (bold red in colour) and shows marks through any scope filter.
- **Network probe** (`main/net-probe.js`, `native/win-net-probe`; `test/net-probe.test.js`): while a window is in a room and "Send telemetry for development" is on (`syncNetProbe` in `main/main.js`: it sends pings to a third party nobody else asked for; turning the checkbox on or off mid-room starts or stops it), main pings this computer's router (the default gateway) and `1.1.1.1` every 200ms, so a stall can be placed: the router slow too is this computer's own network (Wi-Fi, cable, router); only the internet slow is the line past the router; neither is the other person's side or between. Added 2026-11-03 after a ~1s stall delayed both directions by ~800ms between a wired host and a Wi-Fi viewer, and the 2s edge round trip (`er`) missed it on both sides. Windows runs `native/win-net-probe` (C++, `IcmpSendEcho`, no administrator rights; built by `scripts/build-win-app-audio.js`, shipped through `build.win.extraResources`), because ping.exe only pings once a second; macOS and Linux run the system `ping -i 0.2` per target (`createPingParser`: a skipped sequence number, or no reply within 1s, is lost; macOS's "Request timeout" lines are ignored, since at 200ms they fire for replies that are merely slow; a ping that refuses 0.2s for an ordinary user falls back to 1s and logs `network/probe-fallback`). Each `machine-sample` carries `np: {gw: {n, lost?, avg?, max?}, net: {...}}`, and each run of probes over 150ms or lost becomes one `network/probe-stall {on: gw|net, dur, ms?, lost, n}` line (warn) when it ends, or every 10s while it lasts. The gateway's address is never logged. The report's `Likely bottleneck` does not read it yet.
  - **Peer path (M1.13):** the renderer sends main each connection's remote address (`remoteAddress` in `telemetry.mjs`, read from the selected candidate pair and kept out of `readDetail`, so it never reaches the log) over `netprobe:peers` whenever the set changes, and `netprobe:trouble` (`peerTrouble`: ICE disconnected, loss over 10%, RTT over 1s, nothing received for 2s, a host without viewer reports for 4s; at most once per 10s per peer). Main pings each IPv4 peer (4 at most) every 200ms beside the router and 1.1.1.1 (`np.peer: {<peerId>: {n, lost?, avg?, max?}}`; a peer stall is `probe-stall {on: 'peer', peer}`) and traceroutes it 5s after it appears (`why: baseline`), after 3 bad pings once it has answered at least one (`stall`; a router that ignores pings is not a stall), or on trouble, one trace at a time and at most one a minute: `network/trace {peer, why, n, reached, pinged, hops: [[ms|null, kind l/c/p, 4-hex FNV hash]]}`, never an address (`l` private, `c` 100.64/10 carrier NAT, `p` public; the same router hashes the same in both people's logs). The Windows helper takes these on stdin (`peer <id> <ipv4>`, `peer <id> -`, `trace <id>`; prints `p <id> <ms|-1>`, `hop <id> <ttl> <ms|-1> <addr|*>`, `trace-end <id> <0|1>`) and exits when stdin closes; macOS/Linux run `ping` per peer and `traceroute -n -q 1 -w 1 -m 20`. Both samples also carry `cp`, the selected route's own counters over the 2s: `rq/rs` ICE checks sent/answered, `rr/ss` received/answered, `disc`, `in/out` kbps, `rtt`, `quiet` (ms since a packet arrived). The report's **`Where on the path`** line (`scripts/path-verdict.js`) reads all of it around troubled samples (bottleneck's, plus a one-way delay over 1s or a route quiet for 2s): a slow router is that person's home network, 1.1.1.1 alone their provider, pings to each other going bad with both homes clean is the route between (the trouble trace against the baseline names the hop the delay starts at), pings staying clean while the video struggles is the flow alone; `rq` rising with `rs` 0 while `rr` still arrives names the direction that broke.
- `shared/codecs.json`: MediaSource codec strings. The main process uses it for mime types; the renderer uses it to probe `isTypeSupported`.
- `main/turn.js`: optional TURN credentials from an HTTPS broker, with bounded requests, caching and expiry. Packaged `config/turn.json` may contain only `endpoint`; `scripts/check-turn-config.js` rejects bundled secrets. Private user-data `turn.json` may supply static ICE servers. `renderer/network.mjs` renews configuration across friends, rooms and pooled connections. With no configuration, STUN only; `relay/` contains an optional separately deployed broker.

## Verified constraints (don't regress these)

- **Saved-room presence** (`renderer/room-presence.mjs`): Home watches saved codes in `presence:<code>` rooms under the same `APP_ID` as friends and media; active participants watch only their current room. Signed handshakes bind identity to the presence channel, and only peers advertising active membership appear on cards. Observers never join media rooms or count as occupants. Heartbeats expire after 30 seconds; leaving removes names immediately when connected. Channel disposal is serialized before reuse. Presence is live and is not persisted in room history.

- **Connection reuse:** friends, persistent media (`persistent:<code>`) and presence (`presence:<code>`) must retain the same transport `APP_ID`. Separate room IDs isolate their protocols. Changing app IDs disables Trystero's connection reuse and makes room joins depend on discovery even when a friend connection already exists. `npm run test:connections` gates releases on joining, friend discovery and rejoining during a simulated discovery outage; see `docs/connection-regression.md` for the 0.3/0.4 comparison.

- **The rename kept its compatibility anchors.** The app is *Watch With Friends* (GitHub: `onlineslav/watch-with-friends`, titled "Watch With Friends - Synced Media Player"), renamed from *Synced Video Player* after 0.4.3. Three identifiers deliberately still say `synced-video-player`, and changing them breaks existing installs: `build.appId` (`app.syncedvideoplayer`) is how NSIS and electron-updater recognise an install, so a new value would install beside the old app instead of upgrading it; `APP_ID` in `renderer/app.js` and `helloText` in `renderer/friends.mjs` are on the wire, so a new value can't see or connect to anyone on an older build. `main/startup.js` copies the old `%APPDATA%\Synced Video Player` profile into the new one once (`carryOverProfile`, marker file, caches skipped) so identity, friends and saved rooms survive; `scripts/patch-trystero.js` accepts either name's marker so an already-patched `node_modules` isn't patched twice.

- **Entry point is `main/index.js`,** which calls `start()` from `main/main.js`. Electron 44 doesn't set `require.main` to the entry file, so a `require.main === module` check never runs and the app idles with no window.

- **Loop restarts must not look like pauses.** A `<video>` that reaches its end sets `paused` and fires `pause` before `ended`. The host's playing state is `hostPlaying()`, which counts `ended` with loop on as playing; otherwise every loop brings the UI back and viewers see a pause.
- **A looped film's capture tracks leave the stream and stay alive (M1.12).** When a finished film restarts (Loop), Chromium ends the `captureStream()`'s tracks (`readyState` 'ended', no `ended` event) and removes them from its list, adds nothing back, and yet the clones made from them keep carrying the element's picture and sound (`npm run bench -- --variant=loop` heard every repeat). `captureElement`'s `removetrack` therefore only parks the track in `capture.detached`; the next `addtrack` of its kind (a different file) retires and stops it, and a clone's own `ended` retires it. Retiring on `removetrack` silenced every viewer five seconds into the second repeat. Because the capture's list is then empty, `publishStream` (a claim bump in `broadcastState`, `activatePreview`) would have built a stream with the picture alone: it carries over the previous publish's live audio clone when the capture has no live audio track (`session.streamClones`, `unpublishStream(keep)`); `test:network` publishes the looped film twice more and checks both viewers hear it with one audio sender per peer. `test:network` loops a 2.5 s film six times asserting both viewers hear it and never see a pause; the bench's `loop` variant also counts the beeps per repeat and opens a different film afterwards. **A film longer than `KEEP_BEHIND_SECONDS` (15s, `player.mjs`) takes the other path on every loop:** its start was evicted, so `seek(0)` restarts ffmpeg and resets the SourceBuffer (`startAt`/`resetBuffer`) instead of a plain `currentTime` set; the bench's long-film case (20s clip, every restart through ffmpeg) heard both start beeps and decoded ~100 frames in each of 8 repeats with no pause samples, and the capture's tracks leave the stream only on the first loop, the published clones carry on through every restart. `test:network` also asserts both viewers' decoded frames grow in each repeat of its 2.5s loop.

- **The film's sound goes out through Web Audio so a pause doesn't move its timeline (0.8.10).** A `captureStream()` audio clone sends nothing while the `<video>` is paused (`audioSentBitrateBps` 0), and its RTP clock counts samples, so after a pause it is that many seconds behind the picture, which `frames.mjs` stamps with the wall clock. The viewer's lip-sync then held the **sound** back to match: after a 4.3s pause Lenna's `s.av` read -4529, her audio jitter buffer grew 250ms -> 2.2s over ~30s with no loss, "off by about a second" until a seek reset it (2026-11-10). Intermittent: the bench reproduced it in 1 of 2 runs (1259ms late, buffer 2011ms). `filmAudioClone` (`app.js`) publishes `relayAudio(audio, source)` (`renderer/audio-relay.mjs`: the capture's clone into a `MediaStreamAudioDestinationNode`, which renders on the AudioContext's clock, so a pause is silence), falling back to a bare clone; the relay's `stop()` stops the inner clone and an inner `ended` ends it, so the M1.11/M1.12 retire/replaceTrack/carry rules are unchanged. `npm run bench -- --variant=pause` pauses 6s at 11s and gates the offset from 15s after the resume at 120ms: with the relay 4 of 4 runs within ±30ms median; film offset unchanged (21.6ms median, stereo 0.5). `MAX_AUDIO_PATH_MS` is 300 since then (her Bluetooth headphones report 215ms).
- **Only 8-bit video may pass through.** 10-bit HEVC/AV1/VP9 plays locally, but `captureStream` sends WebRTC solid black frames. `copyCodecString` forces a transcode.
- **Stream-copy seeks:** ffmpeg backs input seeks off by ~0.13s for B-frame video and lands on the previous keyframe. `media.js` looks up the keyframe with `ffprobe -read_intervals`, and `plan.js` seeks to keyframe + 0.2s. The MP4 muxer normalizes output timestamps to 0 even with `-copyts`, so the renderer sets `sourceBuffer.timestampOffset = offset`.
- **Local audio/video encode is near-lossless (FLAC, crf 17):** the ffmpeg output only crosses a local pipe to the host's own MediaSource, then WebRTC re-encodes to Opus/H.264, so AAC would add a second lossy audio generation. `planSession` uses FLAC when `support.flac` (probed from `shared/codecs.json`) is true, else AAC; verified Chromium (Electron 44) accepts `avc1.640028,flac` in a SourceBuffer and plays it.
- **Burned-in subtitles** need `-copyts` for correct timing. The `subtitles` filter gets a relative filename with the process `cwd` set to the file's folder, which avoids Windows drive-letter colons in the filter graph. The filename is escaped twice (`escapeFilterValue`). Image subtitles (PGS/VobSub) use `overlay` in `-filter_complex`.
- **New `video.src` means new captured tracks.** The host republishes its stream on `loadedmetadata`. Seeks and track changes keep the same MediaSource, so the stream isn't interrupted.
- **Don't send `captureStream()` video.** It samples on a fixed 30fps timer: 24fps films judder and 60fps is halved. `renderer/frames.mjs` forwards presented frames through `MediaStreamTrackGenerator` instead, and `captureStream()` supplies only the audio. `requestVideoFrameCallback` runs once per rendering frame, so a 60fps film on a 60Hz display lost ~18% of its frames before the sender saw them (bench: the host's own element presented 59.95/s, the viewer got 49; the 60fps share, which does not use this path, arrived at 60); when the callback's `presentedFrames` jumps by more than one, a poll every 8ms also reads the element for the next 2s and a frame goes out once (media timestamp check). After: 58/s presented, interval sd 9.0 -> 6.5ms; 24 and 30fps unchanged (the poll never starts for them).
- **`requestVideoFrameCallback` fires ~1/s while the window is minimized.** `frames.mjs` falls back to polling `new VideoFrame(video)`, skipping frames whose timestamp hasn't changed. Frames are re-stamped with wall-clock time because media timestamps jump backwards on seek.
- **Codec:** `app.js` puts H.264 first via `setCodecPreferences` (hardware encode/decode on Mac and Windows; VP8 is software).
- **Connection telemetry** (`renderer/telemetry.mjs`, pure and unit-tested): every 2s each side reads `getStats()`. The viewer grows its receiver `jitterBufferTarget` from 250ms up to 750ms on freezes, packet loss or jitter, and shrinks it after 30s of calm. It reports what it receives to the host through the `telemetry` action; the host includes its own send limits (`qualityLimitationReason`) in `state`. Both feed the top-bar badge. The sidebar's room list (`renderPeople`, `describePeer`) shows every person: ping comes from each peer connection's own stats, and the host relays each viewer's report in `state.viewers` so everyone sees everyone. Names arrive through the `profile` action. Freezes only count after 4s of uninterrupted host playback (`nextSteady`), because pauses, seeks and ffmpeg restarts (the state's `epoch`) stall the stream on purpose.
- **Log measurements** (M1.2; pure parts in `renderer/telemetry.mjs` `readDetail`/`detailDelta`/`parseOpusFmtp`/`linkFacts`, `renderer/machine.mjs`, `main/machine.js`, `parseProgress` in `main/plan.js`; all unit-tested, and `scripts/check-network.js`'s `checkMeasurements` reads them back out of a real three-window run). They only write to the diagnostic log; nothing acts on them. Every stat is optional (older Chromium, other platforms): an absent one is left out of the line, never `null`/`NaN`, so **absent means unavailable**, and `omitNull` keeps lines small. Keys are short because these lines repeat every 2s. A 2s tick writes, per peer, `host-sample` (host) or `viewer-sample` (viewer), plus **one** `machine-sample` for the whole computer (not per peer: a host with seven viewers would repeat it seven times). Counter deltas are over the 2s since the last reading and are skipped when the ssrc changed or a counter went backwards.
  - `viewer-sample`: `a` audio receive health `{lost, rx (packets), jit (ms), conc, sil (concealed / silent-concealed samples), smp (samples received, to turn those into a ratio), ins, rem (samples inserted/removed for time-stretching), jb (audio jitter-buffer delay ms), lvl (RMS 0-1 from totalAudioEnergy, else audioLevel)}`; `s` A/V sync inputs `{aJb, vJb (jitter-buffer ms per track), aPlay (media-playout delay, audio), aEpt, vEpt, av (= vEpt - aEpt, ms), out, base (the viewer's Web Audio outputLatency/baseLatency, ms: received sound plays through that graph, not the <video>), off (the estimated sound-late offset in ms, `soundLateMs`: what the bench's viewer offset is compared with)}`; `v` decoder cost `{dec (ms per decoded frame), pli, nack, fir (requests this viewer sent), frz, pau (ms frozen/paused)}`; `set`.
  - `host-sample`: `e` encoder cost `{enc (ms per encoded frame), cpu, bw, oth (ms spent quality-limited for that reason), pli, nack, fir (requests received)}`; `set`.
  - `set` on both samples: `{pri: share priority, ab: share audio bitrate, af: 1/0 audio-first}`, so a quality change can be matched to a Settings change.
  - `machine-sample`: `role`; `p` per-process `[cpu% of one core, MB]` for `m` main, `r` renderer, `g` GPU and `o` all others (`[cpu, MB, count]`), from `app.getAppMetrics()`; `free` MB, `bat` (1 on battery), `th` thermal state (macOS only), `lim` OS CPU speed limit % (only after a `speed-limit-change` event); `lt` renderer long tasks since the last sample (`0` none, `{n, ms, max}`, absent = cannot tell); `host` while playing a file: `ff` ffmpeg speed against real time, `ahead` seconds buffered in the MediaSource, `fr` `{n, avg, max, busy}` spacing in ms of the frames `frames.mjs` forwarded (`busy` = presented frames dropped because the previous write was in flight; gaps across a pause or seek are not counted); `cost` ms of main-thread JS the tick spent in its own code (excludes the wait on `getStats`), so the cost of measuring is itself in the log.
  - `link` event (per peer, written when something in it changes, not every tick): `net {p udp/tcp, l/r local/remote candidate type, rp relay protocol, id the candidate pair's id, lf/rf each end's address family (4, 6, `mdns`), nt local network type (wifi/ethernet/vpn, where Chromium says), sw route switches since the connection began}` (the route is the transport's `selectedCandidatePairId`, else the nominated succeeded pair; a new `id` means the route moved, so a blip can be matched to whose end changed; never an address), `venc`/`vdec {impl, hw, codec}`, `opus {local, remote}` `{ch, st stereo, sst sprop-stereo, br maxaveragebitrate, fec useinbandfec, dtx, cbr}` read from the live SDP (re-read only when the streams change and every 30s: each getter copies the whole SDP). The codec mime type is always there; Chromium only names the encoder/decoder implementation and says whether it is hardware (`powerEfficientEncoder/Decoder`) when the page has capture permission, which a plain viewer does not (so `impl`/`hw` are usually absent).
  - `machine/static` (main process, each time a room is entered, so it survives log rotation): GPU feature status table (`app.getGPUFeatureStatus()`), GPU devices (`app.getGPUInfo('basic')`), every display's refresh rate (`hz`) and size, CPU model.
  - **How the numbers reach the sample:** main (`main/machine.js`, started by `app:in-room`) pushes a reading to the window every 2s with `webContents.send('machine:sample')`, a one-way push with no round trip; the renderer keeps the latest and `freshMachine` drops it if older than 6s. `getStats()` is walked once into an array (`Array.from(report.values())`) that `readStats` and `readDetail` both read: walking an `RTCStatsReport` builds a new object per entry on every pass, and the old two-pass code was the bulk of the tick's cost.
  - **ffmpeg speed** comes from ffmpeg's own `-stats` progress line on stderr (`-v error` alone would suppress it): `parseProgress` reads the last whole line and `session:pull` returns `speed` beside each chunk. It is ffmpeg's average since it started, so it drifts toward 1x while the renderer's backpressure holds ffmpeg back; read it together with `ahead`. The failure message uses `lastMessage`, which skips those progress lines.
  - **Measured** (three hidden Electron windows, loopback, 720p24 file with audio): `viewer-sample` about 830 B and `machine-sample` about 315 B per 2s (plus `link` and `machine/static` rarely); main-thread task time per tick 1.0-1.8 ms with the new fields against 4.0-4.2 ms for the old code on the same harness (`MEASURE_BASELINE=1` runs the cost check alone against an older checkout). `estimatedPlayoutTimestamp` is read but this Chromium leaves it undefined in loopback, so `aEpt`/`vEpt`/`av` appear only where it is populated.
- **Send ceiling recovery (M1.7, `chooseSendQuality`):** `npm run bench -- --variant=burst` (10% loss for 4s, clean loopback) cut the ceiling from 7.8 Mbps to 1.7-4.4 Mbps and, at 1080p, the picture to 540p; with three clean reports needed before the first raise it was back at full size 7.6s (median of 3; runs 0.8, 7.6, 10.7) after the burst, and 10.9s after a 30%/3s burst. `RECOVERY_CALM_MS` is now 4000 (two clean reports): 1080p 0.9s (runs 0, 0.9, 8.9), 720p 0.8s, 30%/3s 0.9s (0.9, 0, 2). **The stall memory is deliberate and was left alone:** after trouble the ceiling stays under 85% of the rate that failed for 60s (`SAFE_MEMORY_MS`), so the ceiling itself stands at ~82-87% of its old value at 10s (66% before) and never gets back to it inside 30s; it only shows on content that needs more than that (the bench's testsrc2 needs 7-9 Mbps, a film 3-6). It protects the real Wi-Fi night in `test/sync.test.mjs` where the estimate (7.7-8.9 Mbps) overshot what the link carried (5.9), so a capacity-based exemption would undo it. Freezes after a 10% burst: longest gap between presented frames 267-300ms, no PLI/FIR (NACK retransmission repairs it); at 30% for 3s the gap reaches 550-1134ms because retransmissions are lost too, and Electron 44 has no API to ask for a keyframe sooner.
- **Hardware H.264 encoding (M1.7):** Chromium does not name the encoder (`encoderImplementation` and `powerEfficientEncoder` stay empty without capture permission, so the `link` event's `venc` has only the codec) and `mediaCapabilities.encodingInfo` says `powerEfficient: false` for every codec, so neither proves anything. What does: Windows' `GPU Engine(*engtype_VideoEncode*)Utilization Percentage` counter shows the Electron GPU process using the NVIDIA video-encode engine (up to 12-14%) while the bench film plays and 0 otherwise; `app.getGPUFeatureStatus().video_encode` is `enabled`; and `e.enc` in `host-sample` (encode ms per frame) reads 6.7-7.5ms at 720p60 with no CPU limit. Check it the same way (`Get-Counter` during `npm run bench -- --variant=film --fps=60`) after changing codec preferences.
- **Audio quality (M1.6):** WebRTC's Opus is mono unless the *receiver's* SDP asks for stereo, and the decoder follows the receiver's OWN (local) SDP, so editing only the host's copy of it left every viewer decoding mono (bench: L/R separation 0 at the viewer). The Opus parameters are chosen on purpose in `shared/opus-sdp.mjs` (`preferStereoOpus`): `stereo=1; sprop-stereo=1` (two channels), `useinbandfec=1` (Opus FEC rebuilds a lost packet from the next one), `usedtx=0` (no silence suppression: music and quiet passages keep flowing), `maxplaybackrate=48000` (full band), `maxaveragebitrate=510000` (the format's ceiling; the real cap is the sender's `maxBitrate`); never `cbr`, never `ptime`. It is applied to **every** Opus section of an SDP (a connection that has carried several films has several audio sections), in two places: the remote description in `app.js` (`setRemoteDescription`, which also adds the `x-google-start-bitrate` hint so video doesn't start blurry) and each **local** offer and answer inside Trystero's `peer.mjs` (`scripts/patch-trystero.js`, marker `opus sdp v2`): the argument-less `setLocalDescription()` became create, edit, set, including the ICE-restart offer, with a rollback left alone. Because that is two steps, every description operation in the peer (our offers and answers, remote offers, remote answers) runs one job at a time, each reading the signalling state when its turn comes; a remote offer waits for a local one in flight, then rolls back (a rollback in `stable` throws, which is what a remote offer between `createOffer` and set used to cause). If the edited description is refused the browser's own is used. `test/transport.test.mjs` (a signalling-rule-accurate fake, glare at every timing, ICE restart, refusal) covers the patched dependency; `npm run test:compat` negotiates with a v0.8.0 copy. `parseOpusFmtp` (log line `link`) reads the audio section that carries sound (a track, then not inactive, last wins), not the first. **Congestion ladder (not a loss ladder):** each viewer has its own audio ceiling (`chooseAudioStep` in `sync.mjs`, state `person(id).audio`): the configured cap (`AUDIO_MAX_BITRATE`, or Settings' share bitrate), or a **128 kbps floor** while that viewer's link is congested, one step back up after 30s without congestion. Never lower than 128 kbps, and never triggered by random loss: the bench at 5% random loss measured the same concealment at 64 kbps as at 256 (CELT-mode Opus, which music gets, has no in-band FEC to spend the bits on), and a smaller stream does not make random loss less likely. Congestion means the sender's `qualityLimitationReason === 'bandwidth'` for ~4s (only while the estimate is under 3 Mbps or unknown: with more, the video encoder merely wants more than it needs) or `availableOutgoingBitrate` under 1.5 Mbps for ~10s, neither counting in the first 30s of a connection (the estimate starts near 300 kbps and the encoder reads "bandwidth limited" while it climbs, on any link; the clean-link bench took the step at 2s before this window existed). **It is skipped entirely while "keep audio quality" is on, which is the default**, so by default the audio is always at its configured cap. Logged as `audio-step-change`; `tuneSenders` reads it, and `setParameters` runs once per change (it remembers what it last set per sender, since not every field reads back). **"Keep audio quality"** (`shareSettings.audioFirst`, Settings → Advanced, on by default) means exactly three things: the audio encoding's `priority` and `networkPriority` are set to high (which asks for DSCP marking of its packets, honoured only where the OS and network allow, and tells the encoder it matters), and the ladder above never cuts it. It has no measured effect on how a congested link is split between audio and video: at a 1500 kbps cap the audio got its full 256 kbps with it on or off, and Chromium does not share bandwidth between a connection's audio and video by those priorities without a field trial that Electron does not honour. **One `captureStream()` per element, and sections that go away (M1.11):** every file after the first used to reach viewers with picture and no sound. `publishStream` called `video.captureStream()` again on every `loadedmetadata`; the first capture's listeners survived, took the element's audio copy callback from the second capture and stopped its track. Now `captureElement` captures the host's `<video>` once and keeps it; what is published are `track.clone()`s of the capture's audio (the picture is `frames.mjs`'s generator), and `unpublishStream` stops only the clones and the generator. Chromium does NOT end the capture's old audio track when the source changes: it adds the new file's track and leaves the old one live and silent, one more per file, so the capture's `addtrack` listener stops every audio track before the new one and tells the sink, which retires that clone's sender for 5s and, when the new clone arrives, `replaceTrack`s it onto the same sender (one audio section, the viewer's receiver and track stay, no renegotiation); unclaimed it is released, and a peer whose sender refuses the new clone gets it on a sender of its own (only that peer). Every publish's per-peer promise is checked (`afterPublish`): a failure is logged as `media/publish-failed` (`replace-track-failed` for a refused swap) instead of being swallowed, which is how the glare bug below went unseen. **Sections:** `pc.removeTrack()` leaves the transceiver (with its full codec list) as an m-section nothing reuses, so every film added an audio and a video section for good: ~10 KB of offer per file, over the 64 KiB `@_signal` may be at the 7th film, where the patched receive budget closes the connection to every viewer (a reused connection carries it across rooms). The patched `peer.mjs` (markers `stop transceivers v2` and `v3`) stops transceivers on `removeStream`/`removeTrack` (the section is rejected, then recycled: 5 sections, under 20 KB after 25 files). The rules are in `shared/transceivers.mjs` (`stopSender`, `addSender`; copied beside `peer.mjs` like `opus-sdp.mjs`, and imported by `app.js`), learned the hard way: **stop only once the section was negotiated and the other end does not send on it** (`currentDirection` `sendonly` or `inactive`). A transceiver gets its `mid` from the local offer that first carries it, before any answer; v2 stopped it then, and when that offer was rolled back on glare (the polite end) it was left stopped with no `mid`, in no offer, for good: negotiation "needed" after every round (an Electron probe: 83 `negotiationneeded` in 2s, 280 offers in a 5s run, for as long as the connection lasts), and `addSender`'s idle search did not skip stopped transceivers (setting a stopped one's direction throws). So anything not yet negotiated is only detached (`removeTrack`) and **stays detached**: a first version stopped it once negotiated, and `test:compat`'s new-host-to-0.8.0 glare failed 2 of 6 runs (485a105: 6 of 6), because the old copy's native `addTrack` put its share on that receive-only section in that very window and the later stop rejected it with the share on it (`check-compat.js --host=new --runs=N` prints both ends' descriptions when a glare does not settle). The cost is at most one leftover section per publish taken off within a round trip of being made. `sendrecv`/`recvonly` means the other end sends on it (a copy from before this reuses its receiving transceiver for its own share, as native `addTrack` does; and Chromium hands a detached transceiver to the other end's next section of the same kind, seen in the probe), so it is left detached. `addTrack`/`addStream` make their own transceiver (`addTransceiver`, reusing a detached never-negotiated one, never a stopped one) instead of letting `addTrack` take one of the receiving transceivers the other end made, because stopping our film would otherwise end the share the other end had put on that very section (`test:network` caught this at the first-share step). The signal guard that drops an SDP "without media" (meant for the initial data-channel-only offer) looks for an `m=audio`/`m=video` line instead of `a=rtpmap`; in Electron 44 a real offer that only rejects sections still lists its codecs (and so does its answer), so this only mattered to the fake in `transport.test.mjs`, and older copies accept such offers too. `app.js`'s `stopSendersOf` uses the same `stopSender` for the clones' senders: the room's `removeTrack` cannot, because every room peer is a `shared-peer.mjs` proxy whose `removeTrack` only knows tracks given to it with `addTrack` (`trackOwners`), and these came with `addStream` (`transport.test.mjs` checks this). `unpublishStream` also tells the room to forget each clone (`removeTrack`, for those `trackOwners`). **Known, not fixed (Chromium):** if both ends add a section at the same moment and the two offers give the same `mid` to different kinds (audio on one end, video on the other), the polite end's `setRemoteDescription` after its rollback fails with "RTP extension ID reassignment not supported", whether rollback and set run together or one after another (raw-connection probe); when the colliding new sections match by kind (audio against audio in the probe) it works. Pre-existing and rare (both ends must add media within one round trip), but when it happens the initiator's media does not reach that peer: its offer's resends are refused the same way. A 0.8.0 viewer now sees a receiver track END where it used to see it mute; `test:compat` checks it recovers on the next file. Bench: `--variant=reopen --publishes=10` (files in a row: viewer beep RMS and stereo each time, the host connection's m-sections and offer size); `test:network` opens ten more files on one connection and asserts each is heard, at most 6 transceivers and 6 m-sections (one film is 2, a swap in flight briefly 4), one live audio sender per peer and an offer under 32 KiB (it prints the size: about 8.6 KB, flat), plus a playlist advance. `transport.test.mjs`'s `NegotiatingConnection` (mids, rollback, answers and `negotiationneeded` as Chromium keeps them) covers the glare case: add, offer out, take off, colliding offer, polite rollback, then the next publish, which must settle with no repeated `negotiationneeded`.
- **Packaging:** ffmpeg/ffprobe must be in `asarUnpack` (paths are rewritten `app.asar` → `app.asar.unpacked`). `ffprobe-static` ships every platform's binary, so the per-platform `files` excludes in `package.json` matter. Mac builds are ad-hoc signed (`identity: "-"`) and not notarized.

- **Room protocol v2:** `renderer/protocol.mjs` validates incoming data; every handler is scoped to its creating session. Room admission verifies signed identity challenges. All roles retain the winning logical host revision and state sequence; commands and streams reference that revision. Subtitle paths stay local behind opaque catalog IDs. `renderer/sync.mjs` measures monotonic clock offsets and sets per-viewer bitrate/resolution ceilings from loss, freezes and available bandwidth. Above the 4 Mbps start `chooseSendQuality` climbs one probe per two fresh clean reports, treats a viewer report more than 4s old during playback as trouble (reports share the congested connection), halves on loss over 10%, and for a minute after trouble stays under 85% of the rate actually sent when it began (one clean report between cuts doesn't end that episode: on 2026-11-08 one did, mid-jam, and the memory restarted at the 434 kbps trickling through the jam, holding a clean 12 Mbps link at 360p). These policies are automatic, not Settings controls.
- **Integration check:** `npm run test:network` bundles the real renderer with temporary test hooks and local IPC discovery, then connects three hidden Electron windows over WebRTC. It uses disposable profiles and synthetic files, without public discovery or relay traffic. It covers friends, signed room admission, video/audio, subtitles, controls, host changes, image ordering, terminal errors and rejoining. Production bundles include no test hooks.
