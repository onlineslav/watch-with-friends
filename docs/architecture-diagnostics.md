# Architecture: diagnostic log, telemetry, live view, session context, network probe

Moved word for word from CLAUDE.md on 2026-11-12 so a session doesn't load it every turn. Read before touching `shared/log.js`, `main/log.js`, `main/diagnostics.js`, `relay/`, `main/live.js`, `renderer/context.mjs`, `main/net-probe.js`, or the diagnostics report.

- **Diagnostic log** (`shared/log.js` pure and unit-tested, `main/log.js`, `renderer/log.mjs`): NDJSON, one event per line, in `app.getPath('logs')`. Two 5 MB files rotated by size, not by time, so a fault late in a long film can't push the start of the session out of the file and a crash leaves its evidence behind. The renderer stamps events and ships them to main in batches every 2s (the telemetry sample repeats every 2s per peer, so a write per event would be an IPC message per event); main stamps its own and owns the file. `record` buffers before `start()` opens the file, because a fault during startup is the one worth keeping. **Every line carries both clocks:** the wall clock lines two people's files up against each other, the monotonic clock orders events inside one process, and `clock/offset` records the measured peer offset from `updateClock` so a 2-second control loop can be read across two logs. The load-bearing events are `telemetry/host-sample` and `telemetry/viewer-sample` (every 2s) plus `telemetry/send-quality-change`, which records what `chooseSendQuality` decided and why — that ladder is otherwise invisible from outside, and a viewer cannot tell packet loss from a dipping bandwidth estimate. **Redaction runs in main over every value, not just risky-looking ones,** because the file is meant to be sent to someone else: absolute paths collapse to `…/name.ext` and addresses to `[ip]`, while usernames and room codes are kept because they are the correlation keys. Settings → "Having problems?" writes one combined file through a save dialog and reveals it in the folder. `npm run test:logging` drives the real IPC surface in Electron and asserts no user paths survive an export.

- **Development telemetry** (`main/diagnostics.js`, `relay/worker.mjs`'s `/telemetry`, tested in `test/diagnostics.test.js` and `test/relay.test.mjs`): Settings' "Send telemetry for development" checkbox, **off by default**, uploads the same redacted log automatically: 10s after it's turned on, every 15 minutes while there's anything new, and right after leaving a room. Nothing on quit (holding quit open would fight the updater's relaunch); `main/log.js`'s upload cursor (`upload-cursor.json` beside the log, `takeUnsent`/`commit`, rotation-aware) makes the next launch send what was left, which also covers a crash, and nothing is sent twice. Main owns the setting (`telemetry.json` in userData: `{enabled, from}`) so it can upload before any window exists. The app knows only an address, the `telemetry` key of `turn.json` (`validatePublicConfig` allows it beside `endpoint`); the Worker holds a GitHub token and commits each upload to the private `onlineslav/watch-with-friends-diagnostics` repo as `telemetry/<username>/<day>/<time>.log.gz`. **Reading it:** `npm run diagnostics [username]` (`scripts/diagnostics.js`, uses your own `gh` login) pulls a shallow clone into `work/diagnostics-repo` and writes one file per person per day to `work/diagnostics/<username>/<day>.log`. **Scorecards (M1.3):** `npm run diagnostics -- --report [username] [day]` (`scripts/session-report.js`, pure parts unit-tested in `test/report.test.js` against synthetic logs from `scripts/make-report-fixtures.js`, golden output in `test/fixtures/report-expected/`) prints, per watch session and viewer, typical/worst RTT, loss, frozen share, audio concealment, A/V offset (`s.off`, else `s.av` in older logs, else the same sum from the logged fields; the method is labelled `[off]`/`[av]`/`[delay]`), received vs target video/audio bitrate, encode/decode ms, CPU peak and the quality decisions. A host's file and its viewers' files are paired by room code and overlapping wall clock (sessions split at `room/leave`, a room change or 3 minutes of silence; peer ids become usernames through each file's own `self`). A viewer with no log of its own is filled in from the host's `host-sample` (`receiver` reports), marked as such. `-- --compare [username] [day]` pools every sample by the app version that logged it (the `# upload` header or `app/launch`) and puts a better/worse/same verdict beside the newest build against the previous one. Fields a build did not log print `–`, never 0 or NaN. `--report`/`--compare` fetch the archive first (falling back to the cached files if `gh` fails); `--no-fetch` or `--dir <path>` read what is there. Day defaults to the newest in the archive (`--compare`: all days); `all` or `YYYY-MM-DD` to choose. A build without the `telemetry` key disables the checkbox. Setup steps are in `relay/README.md`. **Live since 2026-11-03:** the Worker is `https://synced-video-relay.watch-with-friends.workers.dev` (Cloudflare account of the repo owner, `npx wrangler deploy` from `relay/`), the GitHub token is its `DIAGNOSTICS_GITHUB_TOKEN` secret (fine-grained, Contents read/write on the diagnostics repo only, no expiry), and CI's `TURN_CONFIG` secret is `{"telemetry":"https://synced-video-relay.watch-with-friends.workers.dev/telemetry"}`, so release builds ship with the checkbox enabled. Adding TURN later means adding `endpoint` to that same secret, not replacing it.
- **Live telemetry** (`main/live.js`, `shared/live.js`, `relay/live.mjs`, `scripts/live-view.js`; tests in `test/live.test.js`, `test/live-relay.test.mjs`): the same checkbox also streams each log line as it happens, so `npm run diagnostics -- --live [scope|scope/event] [--from name]` shows everyone's lines interleaved by their own clock (held up to 3s to reorder, labelled by username, your `gh` login sent in an `Authorization` header). The tap is `log.subscribe` in `main/log.js`: it hands over the exact strings written to the file (so they are redacted; the page does nothing extra, nothing runs in the renderer). One WebSocket per app to `/live?role=app&from=<username>` (opened only while the checkbox is on and the username is known; closed at once when it's turned off); the Durable Object `LiveHub` (hibernating, SQLite-backed, `ping` answered by `setWebSocketAutoResponse`) tells apps `{"watching": bool}` and apps send **nothing while nobody watches**. Frames are `[version byte][raw deflate against shared/live-dictionary.txt]` of the batch, at most one a second; measured 0.4–1.4 kbps per person (host with 3 viewers 1.35 kbps, raw 12.6), `npm run test:live-rate`. Rebuilding the dictionary (`scripts/build-live-dictionary.js`) means a new `VERSION` in `shared/live.js`. Reconnect backs off 1s→60s with jitter, at most 4 attempts a minute; a ping unanswered for 10s drops the socket (one every 15s, one every 2s while in a room: see the edge round trip under *Session context* below); while down the sender holds at most 60s / 256 KB and says `live/dropped` how many it lost. Readers are authorized by asking GitHub whether their token can read the diagnostics repository (401 no/bad token, 403 no access, 503 GitHub unavailable; cached per token hash). App sockets are unauthenticated like `/telemetry`: the caps (64 apps, 8 readers, 64KB frames, 5 frames/s) and the reader's control-character stripping are the defence. `npm run test:live` drives the whole chain against `wrangler dev` with your own `gh` login. The renderer batches its log IPC every 1s and main flushes every 0.5s so a line is on the stream ~2s after it happens.
- **Session context, marks and "whose network" (M1.9; pure parts in `renderer/context.mjs`, `renderer/protocol.mjs` `cleanMark`, `renderer/sync.mjs` one-way delays, `main/context.js`, `main/plan.js` `sourceFacts`, `scripts/bottleneck.js`; tests `test/context.test.mjs`, `test/context-main.test.js`, `test/mark-wire.test.mjs`, `test/bottleneck.test.js`, `test/report-marks.test.js`, `test/live-view-mark.test.js`; `check-network.js`'s `checkContext` and `check-live.js` read the real log).** All of it only writes log lines; nothing acts on them. Every line goes through the usual redaction and stays far under the 4000-byte cap (longest new one measured 273 B); none runs on a timer, so there is no rAF loop and no extra IPC (the edge RTT rides the machine reading main already pushes every 2s).
  - **Marks:** the `mark` room action (a room action of its own, `protocol.mjs` `cleanMark`: `{id, note?}`, id 6-16 chars of `a-z0-9`, note at most 80 characters with controls stripped; the same id again adds a note). The key is `X` (`MARK_KEY` in `context.mjs`; Shift+X focuses the note box; Settings shows it) and the flag button in the controls; the person's own press writes `mark/note {id, src:'self', by, note?, pos, playing}` and sends it, every peer writes `src:'peer', by, peer`. Rate-limited to 6 marks/notes per 10s per sender on both ends (`MARK_LIMIT`, `MARK_WINDOW_MS`). A mark touches no host, claim or stream state, so it is safe during a host change. **Compatibility:** copies from 0.7.x/0.8.0 never register `mark`, and every build since 0.7.0 carries the Trystero patch (`if (!action) return` in `handleData`) that drops a frame for an unregistered action before any handler, budget or error runs; `test/mark-wire.test.mjs` runs two real wire managers (one without `mark`) and checks that nothing is thrown, warned or closed and the other actions still arrive in order; `check-network.js` also sends a bad mark and an action nobody registered between real windows. The `telemetry` message gains an optional `at` (see below); `cleanTelemetry` reads only `message.receiver`, so an older host ignores it, and a newer host without it just logs no viewer-to-host delay.
  - **Edge round trip:** `main/live.js` pings its `/live` socket (answered `pong` by `setWebSocketAutoResponse`, so the Durable Object stays asleep) and times it on a monotonic clock; `setFast(true)` (main calls it on `app:in-room`) makes that every 2s instead of every 15s, with one ping outstanding at a time and the 10s dead-socket rule counted from the first unanswered ping. `edgeRtt()` is the last answer if it is under 6s old, and `main/machine.js` puts it on the machine reading as `er` (ms), so it appears on `machine-sample`, per computer, whether or not anyone is watching live; it needs the "Send telemetry for development" checkbox on (that is what opens the socket) and is absent otherwise. Pings are counted in the sender's `wireBytes`, so `npm run test:live-rate` includes them (3 peers on the host 1.46 kbps, worst viewer 1.07). Worker unchanged: the auto-response was already deployed with M1.1. On Cloudflare's free plan each ping is a fraction of a request (WebSocket messages count 20:1): about 1,800 an hour per person in a room.
  - **One-way delay per direction:** `sync.mjs` `hostToViewerMs`/`toHostClock`/`viewerToHostMs`, from the clock offset `updateClock` already measures (host clock = ours + offset). The viewer takes each `state`'s `sentAt` against its arrival (the worst since the last sample goes on `viewer-sample` as `ow.hv`); the viewer stamps its `telemetry` report with `at` = its time plus the offset, and the host's reading of how late that is goes on `host-sample` as `ow.vh`. The offset assumes both directions are equal, so **only a rise means anything** (a queue building in one direction moves that direction's number and not the other's); negative values near zero are logged as they are.
  - **Context events:** `audio/device` (`why: room|change`, `kind` builtin/wired/bluetooth/hdmi/virtual/unknown from the label by `classifyAudioDevice`, `label` of the real device behind "default", `outs`, `sr`, `base`/`out` latency ms; labels are empty until media permission, which gives `unknown`, never an error); `crash/render-process-gone`, `crash/child-process-gone` (GPU, utility; reason, exit code), `crash/unresponsive|responsive`, `window/state` (minimized, restored, shown, hidden, focused, blurred, maximized, fullscreen; main, from BrowserWindow events), `window/fullscreen` and `window/visibility` (renderer), `power/state` (suspend, resume, lock, unlock, ac, battery, shutdown; the line before sleep is flushed), `action/<play|pause|seek|loop|audio|subtitle|volume|mute>` (`via: host|viewer|remote`, `from` for a command the host received; volume is debounced to one line per drag), `settings/change` (share settings; a device id is only "device") and `settings/save` (zoom, telemetry, "name changed"), `network/peer-state` now carries `change: {on, from, to}` and `network/ice-restart {connection, reason: transport|config-change|reconnect}`. Lines from main carry no room code; the report attaches them to the watch session they fall inside by time.
  - **Source facts:** `media/source` (main, from `sourceFacts` in `plan.js`) once per file opened and again when the conversion changes (a retry, a burned-in subtitle, another audio track): `c` container, `dur`, `mode` copy|transcode|audio, `v {codec, pix, w, h, fps, hdr}`, `why` (`pixel-format`, `codec`, `no-decoder`, `burn-in`, `retry`), `enc` (nvenc/qsv/amf/videotoolbox/libx264), `tm` (HDR tone-mapped), `a {codec, ch}`, `af` flac|aac, `sub`.
  - **The report:** `npm run diagnostics -- --report` lists each mark (merged by id across logs, timed by the presser's clock, last note wins) with the viewer/host numbers from 5s either side of it and the context lines within 10s, and each viewer gets `Edge RTT`, `One-way delay` and **`Likely bottleneck`** lines. `scripts/bottleneck.js` compares troubled samples (loss over 2%, a freeze, the encoder held back by bandwidth or CPU) with calm ones: a link full of our video makes **its own** edge RTT climb by 40 ms and 1.5x while the other person's stays flat, which names that host's upload or that viewer's network; an encoder held back by CPU, slow encodes or long renderer tasks (a rate: 100 ms per troubled sample, so one stray task in a long session is nothing) is the host's computer, and slow decodes or long tasks the viewer's, but only while **neither** link is full (a computer is never blamed while the other side's link is full); both links up, neither up, or no `er` at all is `unclear` with the reason. `--live` prints a mark as `>>> MARK by <who> "<note>" <<<` (bold red in colour) and shows marks through any scope filter.
- **Network probe** (`main/net-probe.js`, `native/win-net-probe`; `test/net-probe.test.js`): while a window is in a room and "Send telemetry for development" is on (`syncNetProbe` in `main/main.js`: it sends pings to a third party nobody else asked for; turning the checkbox on or off mid-room starts or stops it), main pings this computer's router (the default gateway) and `1.1.1.1` every 200ms, so a stall can be placed: the router slow too is this computer's own network (Wi-Fi, cable, router); only the internet slow is the line past the router; neither is the other person's side or between. Added 2026-11-03 after a ~1s stall delayed both directions by ~800ms between a wired host and a Wi-Fi viewer, and the 2s edge round trip (`er`) missed it on both sides. Windows runs `native/win-net-probe` (C++, `IcmpSendEcho`, no administrator rights; built by `scripts/build-win-app-audio.js`, shipped through `build.win.extraResources`), because ping.exe only pings once a second; macOS and Linux run the system `ping -i 0.2` per target (`createPingParser`: a skipped sequence number, or no reply within 1s, is lost; macOS's "Request timeout" lines are ignored, since at 200ms they fire for replies that are merely slow; a ping that refuses 0.2s for an ordinary user falls back to 1s and logs `network/probe-fallback`). Each `machine-sample` carries `np: {gw: {n, lost?, avg?, max?}, net: {...}}`, and each run of probes over 150ms or lost becomes one `network/probe-stall {on: gw|net, dur, ms?, lost, n}` line (warn) when it ends, or every 10s while it lasts. The gateway's address is never logged. The report's `Likely bottleneck` does not read it yet.
  - **Peer path (M1.13):** the renderer sends main each connection's remote address (`remoteAddress` in `telemetry.mjs`, read from the selected candidate pair and kept out of `readDetail`, so it never reaches the log) over `netprobe:peers` whenever the set changes, and `netprobe:trouble` (`peerTrouble`: ICE disconnected, loss over 10%, RTT over 1s, nothing received for 2s, a host without viewer reports for 4s; at most once per 10s per peer). Main pings each IPv4 peer (4 at most) every 200ms beside the router and 1.1.1.1 (`np.peer: {<peerId>: {n, lost?, avg?, max?}}`; a peer stall is `probe-stall {on: 'peer', peer}`) and traceroutes it 5s after it appears (`why: baseline`), after 3 bad pings once it has answered at least one (`stall`; a router that ignores pings is not a stall), or on trouble, one trace at a time and at most one a minute: `network/trace {peer, why, n, reached, pinged, hops: [[ms|null, kind l/c/p, 4-hex FNV hash]]}`, never an address (`l` private, `c` 100.64/10 carrier NAT, `p` public; the same router hashes the same in both people's logs). The Windows helper takes these on stdin (`peer <id> <ipv4>`, `peer <id> -`, `trace <id>`; prints `p <id> <ms|-1>`, `hop <id> <ttl> <ms|-1> <addr|*>`, `trace-end <id> <0|1>`) and exits when stdin closes; macOS/Linux run `ping` per peer and `traceroute -n -q 1 -w 1 -m 20`. Both samples also carry `cp`, the selected route's own counters over the 2s: `rq/rs` ICE checks sent/answered, `rr/ss` received/answered, `disc`, `in/out` kbps, `rtt`, `quiet` (ms since a packet arrived). The report's **`Where on the path`** line (`scripts/path-verdict.js`) reads all of it around troubled samples (bottleneck's, plus a one-way delay over 1s or a route quiet for 2s): a slow router is that person's home network, 1.1.1.1 alone their provider, pings to each other going bad with both homes clean is the route between (the trouble trace against the baseline names the hop the delay starts at), pings staying clean while the video struggles is the flow alone; `rq` rising with `rs` 0 while `rr` still arrives names the direction that broke.
