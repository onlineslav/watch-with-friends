# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```sh
npm install
npm start                        # esbuild-bundles the renderer, then launches Electron
npm test                         # all unit tests (node:test, finds test/*.test.{js,mjs})
node --test test/plan.test.js    # a single test file
npm run bundle                   # renderer/app.js -> renderer/bundle.js (generated, gitignored)
npm run test:logging             # end-to-end check that renderer events reach the log file
npm run dist:win                 # NSIS installer in dist/
npm run dist:mac                 # .dmg in dist/, only works on macOS (CI builds both, see .github/workflows/build.yml)
```

- `renderer/bundle.js` is what the window loads. Re-run `npm run bundle` after editing anything in `renderer/` or `shared/`.
- VS Code terminals set `ELECTRON_RUN_AS_NODE=1`, which makes Electron run as plain Node so `require('electron')` fails. `npm start` goes through `scripts/electron.js`, which removes it; run Electron directly (`electron .`) and you have to unset it yourself.

## Architecture

A small-room watch-together app (up to eight people). There is no server: peers find each other through Trystero's public Nostr relays and then connect directly over WebRTC.

**Media path (host only):** file → ffmpeg (main process) → fragmented MP4 on stdout → renderer pulls chunks over IPC → MediaSource on the host's `<video>` → `video.captureStream()` → WebRTC → viewer's `<video>`. The viewer never has the file. Its picture and sound come through the WebRTC stream; text subtitles come separately as cues. Images are the exception (see **Pictures**).

**Pictures:** an image file isn't streamed. `media.readImage` returns its bytes (formats Chromium can't show are converted to PNG by ffmpeg, `imageConvertArgs`), and the host sends them over the `image` action with `{id, name, mime}` metadata, to everyone on open and to each peer that joins. The host's `state` carries `image: {id}`; viewers keep the last picture per sender (`session.images`) and show it once the ids match. Extensions, Chromium mime types and the 50 MB cap live in `shared/images.json`. While a picture shows, the controls stay visible (volume still sets reaction sounds) but `control` ignores play/seek/loop.

**Screen sharing:** the host can share a whole screen or a window instead of opening a file. The picker is our own (`renderer/screenshare.mjs` shapes `desktopCapturer`'s source list for the thumbnail grid; `openSharePicker`/`startShare` in `app.js`), not the OS one: the renderer lists sources over `screenshare:sources`, the user picks one, `screenshare:select` tells `main/main.js` which id to trust (and whether system-audio loopback was requested), and only then does `navigator.mediaDevices.getDisplayMedia` resolve through `session.defaultSession.setDisplayMediaRequestHandler` — main only ever grants an id it just listed and the renderer just selected. A share claims host exactly like opening a file (`startShare`, same `claimedAt`/`isNewerClaim` dance) and publishes through `publishShareStream`, a leaner sibling of `publishStream` since a share's tracks are never swapped mid-session the way the file pipeline's are; viewers watch it through the same WebRTC path a video uses. Sharing has no timeline: `state.screen: {id, name, audio}` plays the role `image: {id}` plays for pictures, and `control` already ignores play/seek/loop because nothing is loaded. **Several people can share at once.** Only the first share claims host (that is what stops a movie); while anyone else's share is showing (`othersSharing`), a new one runs *alongside* it (`session.screen.alongside`) without touching the host or the role. Every sharer announces its own share on the `share` action (`{id, name, audio}`, or `{id: null}` on stop; `cleanPeerShare`), and its stream carries `claimedAt: Number(id)`. Viewers never put a share on `<video id="remote-video">`: the share grid (`renderShares`, laid out by the pure `shareTiles`/`shareView`/`gridColumns` in `screenshare.mjs`) gives every share, your own first, a tile with its own `<video>`, and the host's share is also read from its state so an older build still shows. Each other person's tile mixes its sound through its own gain (the tile's mute button) into the app output (`routeTileAudio`); your own tile is silent. Tabs (All / You / names) or a click on a tile switch between all tiles and one full size. A movie, picture or YouTube video ends every share (`receiveState` stops an alongside share on any non-share, non-idle state); the host stopping its share leaves the others running. Never put a live `MediaStream` on `<video id="local-video">`: it is wired to the file pipeline's `loadedmetadata`/`ended` listeners. Stopping — the Stop button, or the track's own `ended` event when the OS/browser share UI ends it — unpublishes and returns to idle the same way; switching source, or changing the audio source in Settings, is stop then start again (`restartShare`); resolution and frame rate apply live instead, via `track.applyConstraints()` (`applyShareVideoConstraints`), since a capture track tolerates that without restarting. **Audio quality** (Settings' bitrate choice, up to 510kbps — Opus's own practical ceiling, matching `maxaveragebitrate` in `lib.mjs`'s `preferStereoOpus`) needs no explicit re-apply at all: `tuneSenders` already runs once a second for every host and just reads `shareSettings.audioBitrate` instead of the fixed `AUDIO_MAX_BITRATE` whenever `session.screen` is active, so a Settings change takes effect on its own within a second, same as the adaptive per-viewer video bitrate already does.

**Share priority** (Settings, `sharePriority` in `screenshare.mjs`: Balanced / Sharp text / Smooth motion) sets the share track's `contentHint` and the senders' `degradationPreference` in `tuneSenders` (files always `maintain-framerate`); Sharp text also skips the 1080p downscale (bitrate still adapts), and a change applies live.

**Screen-share audio** defaults to `audioDeviceId: 'system'` on macOS and `'app'` on Windows (`DEFAULT_SHARE_AUDIO`; Windows settings saved before `'app'` existed there are moved over once, the `winAppAudio` marker). `'system'` is `audio: 'loopback'` in the display-media handler, requested only when Settings' audio source is "System audio", never unconditionally. Electron's own `Streams.audio` doc comment says this is Windows only — that's stale against the installed version; verified directly (a standalone probe script, not through the app) that Electron 44 captures it on macOS too via Chromium's CoreAudio Tap integration, live and labeled "System audio" even when the shared source is a single window. It is **whole-system** audio either way, not isolated to the shared app. Settings' audio-source picker (`renderer/screenshare.mjs`'s `audioInputs`, shaped from `enumerateDevices()`) covers isolating one app two ways: a specific input device captured with `getUserMedia`, merged into the share's stream (`captureShareAudio` in `app.js`) — a virtual device such as BlackHole routes one app's output into this as an input, on any platform — or the `'app'` option (macOS and Windows), which gets real per-app isolation from the OS's own API. With `'app'`, a whole-screen share falls back to system audio (`audioSource` in `startShare`), since there's no single app to scope to.

**Both `getDisplayMedia`'s and `getUserMedia`'s audio requests need `SHARE_AUDIO_CONSTRAINTS` (`channelCount: 2`, `echoCancellation`/`noiseSuppression`/`autoGainControl: false`), never a bare `audio: true`.** Verified directly: an unconstrained loopback request comes back `channelCount: 1` with all three processing flags on — Chromium's defaults are tuned for a voice call, not for sharing music or system audio, and silently downmix to mono and run voice DSP over it unless told otherwise. `captureShareAudio`'s native/`'app'` path doesn't need this — `native/mac-app-audio` already asks ScreenCaptureKit for 2 channels directly — but anything going through a browser `getUserMedia`/`getDisplayMedia` call does.

**Diagnosing "no audio" reports for a share**, in order: (1) `appaudio`/`screenshare` log events (`main/app-audio.js`, `app.js`) say whether capture started, whether any bytes ever arrived (`appaudio receiving`), and the exact signal name plus a `DiagnosticReports` pointer if the native helper crashed; (2) `sampleTrackAudioLevel`/`sampleAudioLevelFromNode` (`app.js`) tap a throwaway `AnalyserNode` onto the host's outgoing track right after publishing, and onto each incoming share track in `routeTileAudio`, logging the measured RMS (`screenshare audio-level` / `received-audio-level`) — this is the only check in the chain that answers "is this actually sound, not silence," independent of whether every other layer claims success. A non-zero level on the host but zero (or absent, if the event never fires because the stream never attached) on the viewer narrows it to WebRTC transport or the viewer's own output device, not capture.

**Actual achieved audio bitrate** (not the configured ceiling `tuneSenders` sets, the real thing `getStats()` measures) needed its own fields in `telemetry.mjs`'s `readStats`: `audioOnly` there only ever substitutes audio for the video-shaped `inbound`/`outbound`/`inboundRtp`/`outboundRtp` fields when there's no video at all, so a share (video and audio sent together) was invisible to it. `audioInboundRtp`/`audioOutboundRtp` are separate, always-populated counters alongside those, unconditionally — logged as `audioSentBitrateBps` (`telemetry host-sample`) and `audioReceivedBitrateBps` (`telemetry viewer-sample`) via the same `bitrateDelta` byte-counter-over-time math the video fields already use. Opus is VBR, so this can read well under the configured cap for quiet content — that's expected, not a bug by itself.

**The `'app'` audio option** runs `native/mac-app-audio` (`main/app-audio.js` spawns it, `renderer/app-audio.mjs` consumes it), a small Swift tool built from source by `scripts/build-mac-app-audio.js` (`prebundle`'s `--if-needed`, or `prepare-package.js`'s `beforePack` hook for a release build — the committed source is the review surface, not a vendored binary, unlike the kind of third-party native addon this avoided pulling in). It takes the CGWindowID from a `window:<id>:<n>` desktopCapturer source (`windowIdFromSource`; `startShare` never passes `'app'` for a whole-screen share), resolves that window's owning `SCRunningApplication` via ScreenCaptureKit, and streams that app's audio alone — the same capability Discord's own "Application Audio" option on macOS uses, confirmed by having Discord's public-facing docs describe it and matching it to ScreenCaptureKit's content-filter API, not by decompiling Discord. It writes raw interleaved Float32 PCM to stdout (one line of `ready` or `error: ...` on stderr first, so the main process knows whether it actually started), pulled with the same backpressure-by-polling pattern as media.js's ffmpeg sessions (`appaudio:start/pull/stop`), and turned back into a `MediaStreamTrackGenerator('audio')` track in the renderer the way `frames.mjs` does for video.

**On Windows the `'app'` option runs `native/win-app-audio`** (C++, built by `scripts/build-win-app-audio.js` with the MSVC tools vswhere finds, static CRT; same `--if-needed`/`beforePack` hooks, shipped through `build.win.extraResources`). It speaks the same stdout/stderr protocol as the Mac helper, so `main/app-audio.js` and `renderer/app-audio.mjs` are shared. On Windows a desktopCapturer window id is the HWND; the helper resolves its PID (a Store app's `ApplicationFrameHost.exe` frame is followed to the hosted app's process) and captures it with WASAPI process loopback, `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE`, so child processes (browser audio services, plugin hosts) are included and nothing else is — this is what stops Discord's voice from riding along on a window share. It refuses this app's own window (the target is its parent process), since that would echo everyone back. Process loopback only delivers packets while the app is rendering sound, so the helper fills gaps with wall-clock-paced silence (only after 100ms without a packet, so it never cuts into real sound, and at most 100ms at a time, so a stdout stall resyncs instead of bursting zeros). Errors after `ready` (the app quitting) go to stderr as `error: ...` and `main/app-audio.js` keeps the last one as the session's error. **Any change to `main.cpp` needs `node scripts/check-win-app-audio.js`** (plays two quiet tones; by hand only, it makes sound): it checks one window's tone comes through and another process's doesn't, real-time rate through silence and through sound starting mid-capture, and the closed-window and app-exit errors. A clean compile proves none of that. An app using ASIO or WASAPI exclusive mode (common in DAWs) bypasses the Windows audio engine, so neither this nor system loopback can hear it.

**Two more things in `native/mac-app-audio/main.swift` that only broke once real audio was actually flowing, and that a clean compile — or a test against a silent app — will not catch:**

- **`extractPCM`'s `AudioBufferList` allocation must be sized by querying `bufferListSizeNeededOut` first, never `MemoryLayout<AudioBufferList>.size`.** That struct has a flexible array member (`mNumberBuffers` then that many `AudioBuffer` entries); the fixed Swift size only covers one, so a first version of this crashed the instant real stereo (two-buffer, planar) audio arrived.
- **`SCStream` must be held in a variable that outlives the `do` block that creates it.** A `let stream = SCStream(...)` declared inside `do { ... }` goes out of scope — and ARC deallocates it, silently tearing down capture — the instant that block ends, right after `startCapture()` resolves and "ready" is printed. No crash, no error: every subsequent capture callback just never fires again, because there is no stream left to fire it. Fixed by declaring `var stream: SCStream?` before the `do` block and assigning into it on success.

Both were found the same way: testing against an app genuinely playing audio, not a silent one (the first via `main/app-audio.js`'s "exited with code null" — killed by a signal — in the diagnostic log; the second via a standalone instrumented copy that logged every step of `extractPCM` and the raw stream callback, which showed the callback firing in an equivalent top-level test script but never firing at all from the real file — the output of a `diff` in behavior that line-by-line code reading had missed twice). Both were confirmed fixed by capturing real, continuous, non-silent PCM from a live stream for several seconds with the actual compiled binary, not by compiling cleanly — this file has compiled cleanly through every one of these bugs. Any future change to this file needs that same real-audio test before it can be called done.

**A host with nothing to show** (just stopped a share, with no file, image or YouTube video either) is a state `stateIsIdle` (`protocol.mjs`) recognizes — distinct from a file that's still opening, which already has a `playlistId` by the time it claims host. `receiveState` runs the same recovery for this that `onPeerLeave` runs for a host that's actually gone (clear `hostId`/`remote`, detach the stream, `setRole('idle')`), instead of leaving every viewer stuck as `'viewer'` with a frozen last frame and no way to host next — the only way back out used to be leaving and rejoining the room. Any future kind of hosted content that can end up with nothing to show needs this same check, or it regresses the same way.

- `main/plan.js`: pure decisions, unit-tested. Pass video through vs. transcode to H.264, ffmpeg args, subtitle burn-in filter graphs, HDR tonemap. Change behaviour here, not in `media.js`.
- `main/media.js`: runs ffprobe/ffmpeg. Detects a working hardware encoder once (nvenc/qsv/amf/videotoolbox, else libx264). Sessions are pull-based: `pull()` drains stdout, and ffmpeg blocks when the renderer stops pulling.
- `renderer/player.mjs`: the MediaSource pipeline. Seeking inside the buffer is a plain `currentTime` set. Seeking outside it, or changing audio/subtitle track, restarts ffmpeg at that time and resets the SourceBuffer (`abort`, `changeType`, `remove`). Keeps about 45s buffered ahead. If Chromium fails to decode a passthrough stream, it retries once with `forceTranscode`.
- `renderer/app.js`: the room and sync layer. The host is authoritative. It broadcasts a `state` action once a second and on every media event. The viewer interpolates time from it and sends `command` actions (play/pause/seek/loop/audio/subtitle), which the host applies. Whoever opens a file claims host; when two claims collide, the newer `claimedAt` wins (`isNewerClaim`).
- **Subtitles are per person.** Text tracks are converted to WebVTT by ffmpeg (`subtitleExtractArgs`, `parseWebVtt` in `plan.js`, cached in `media.js`) and drawn over the video by each app (`renderer/subtitles.mjs`). Viewers fetch a track's cues from the host with the `cues` request action; a subtitle file a viewer loads is read from their own disk and never shared. The viewer delays captions by the measured jitter-buffer delay (`delayMs` from `inboundDelta`) because its picture trails the host's clock. Image subtitles (PGS/VobSub) are still burned in by the host, so they are shared; the renderer never asks `planSession` to burn in a text track.
- **Whiteboard** (`renderer/whiteboard.mjs`, pure and unit-tested): points are stored relative to the video picture (`pictureRect`, object-fit: contain), so drawings line up on any window size. The `board` action carries `stroke` chunks while drawing (idempotent, keyed by coordinate `offset`), `clear` (removes strokes started at or before `at`, the same rule on every peer), and a `sync` snapshot sent to each joining peer. Incoming colours and sizes are validated against the palette. The eraser is an ordinary stroke whose colour is `ERASER`, drawn with `destination-out`, so it syncs, clears and snapshots like any other stroke.
- **Playlist and saved rooms** (`renderer/playlist.mjs`, `renderer/room-history.mjs`, unit-tested): owners are authenticated usernames, resolved to current transport peer IDs in `app.js`. `RoomHistory` stores room name, playlist order/removals, per-item progress, current cursor, loop and claim watermark in localStorage scoped to identity and room code. Only these local records contain `ownFiles` paths; network snapshots never grant file capabilities. Leaving clears session paths after saving. Home lists saved rooms and lets a member leave by deleting their local copy and closing its presence watcher; other members retain their copies, so the decentralized room disappears when the final copy is removed. Resume skips unavailable owners, and `StreamPlayer.open(path, start)` restores progress. Playlist `add`, `remove`, `move`, `sync` and `play` actions retain their merge rules; `availability` advertises only file IDs checked locally through IPC. Checkpoints use host claim/sequence ordering, persist on state updates/exit, and merge on rejoin. End-of-media skips unavailable items; when a playing host leaves, the remaining peer with the lowest transport ID advances the queue. Persistent rooms use prefixed room IDs under the same transport app ID as friends (see Connection reuse below). The playlist drawer and its drag/reorder geometry remain in `playlist.mjs`, while `overlay.mjs` controls the tab's contrast over the picture.
- **Reactions** (`renderer/reactions.mjs`, `renderer/confetti.mjs`, both unit-tested): the room's `react` action carries only a reaction kind, checked against `REACTIONS` and rate-limited per sender on both ends. Sounds are synthesized with Web Audio (no audio files) through a gain set to the app's volume. Confetti is a full-window canvas animated only while pieces are on screen.
- **Identity** (`renderer/identity.mjs`): each install keeps an ECDSA P-256 key pair in `localStorage`. The username is a handle the person picks plus a tag, `handle#xxxx-xxxx`: 8 Crockford base32 characters hashed from the handle and public key, so it can be checked against the key (faking one takes ~2^40 key pairs). A new install, or an identity saved before handles existed, boots into the welcome screen (`showWelcome`) and only reaches home once both a username and display name are saved. The username can't be changed from home: the gear (top left on home, first in the room's top bar) opens Settings (`showSettings`), an overlay that moves inside `.room` while you're in one so it still shows in fullscreen. Its "Change username" reopens the welcome screen with a new key pair, so it's disabled inside a room. The display name (`renderer/profile.mjs`) is separate, editable only in Settings (your own room-list row just shows it, tagged "you"), and cleaned with `cleanDisplayName` both when typed and when received.
- **Friends** (`renderer/friends.mjs`, `FriendNetwork`, protocol tested against an in-memory Trystero in `test/friends.test.mjs`): no server. There's one friends list (`#friends`): it slides in from the left on home and floats over the video on the left in a room (`enterRoom`/`leaveRoom` move it, `setFriendsOpen` toggles it; the room list's "Invite friends" opens it too). It shows your username to copy, and the toggles' dot means a friend is online (green) or a request is waiting (accent). Each app waits in `inbox:<username>`. Adding someone joins `pair:<a>:<b>` (sorted) and, until they acknowledge the request, their inbox. Accepting a request adds them back, so both meet in the pair room. Every peer must first send a hello signed over the room id and both peer ids (`helloText`, `verifySigned`); other messages from unverified peers are queued until then. Presence rides on the pair room's `profile` message (`status: {inRoom, hosting, title}`, cleaned by `cleanStatus`); `syncPresence` in `app.js` resends it whenever your status changes, and it's forgotten as soon as the friend goes offline. Asking to join uses the pair room's `join` message (`ask`, then `invite` with the room code or `declined`); an answer is only honoured if you asked that friend within the last 2 minutes, so nobody can pull you into a room. Inviting a friend from inside your room sends `offer` with the code (`inviteToRoom`); it only shows them a card (`receiveJoinOffer`), and they join if they click Join. Trystero's `selfId` is the same in every room, so anything keyed by peer id must also check which room it came from.
- **Trystero transport patch (pinned 0.25.4):** `scripts/patch-trystero.js` runs after installation and before tests/bundling. It prevents departed-room frame replay, bounds reassembly and handshake queues, expires abandoned chunks, and reports stalled sends. `test/transport.test.mjs` covers the actual dependency; `npm run test:network` checks repeated rejoining while friend connections stay alive. Review these patches before upgrading the dependency.
- **Auto-update** (`main/updater.js`, Windows only): at launch, packaged builds check the GitHub releases with `electron-updater` (the `build.publish` config puts `app-update.yml` in the app), download a newer version and install it silently with a relaunch. The renderer reports `app:in-room`; a download that finishes during a room waits until you leave it (or quit). Releases must carry `latest.yml` and the `.exe.blockmap`, which the workflow uploads. Mac can't auto-update (Squirrel.Mac rejects ad-hoc signed apps), so `checkMacUpdate` reads the latest release from the GitHub API and home shows a card whose Download opens the `.dmg` for `process.arch` (`macUpdate` in `main/release.js`, pure and unit-tested). Main only opens the URLs it found itself.
- **UI scale** (`main/zoom.js`, `renderer/zoom.mjs`, both pure and unit-tested): Electron's zoom factor scales the page, video included. Electron's default menu already binds these keys, but its zoom-in accelerator is `CommandOrControl+Plus`, which needs Ctrl+Shift+= on a US keyboard, so `watchZoom` takes Ctrl `+`/`-`/`0` and Ctrl+wheel with `before-input-event` + `preventDefault` and forwards a direction to the renderer. The renderer owns the scale: Settings has a slider and a typed percent box over a free 50–200% range (`clampZoom`, `parseZoom`), while the keyboard jumps between `ZOOM_STEPS`. It's saved in `localStorage` as `uiScale`. Keyboard and wheel changes flash `#zoom-badge`, which is a button that resets to 100% and, being `position: fixed`, is moved into `.room` so it survives fullscreen.
- **Pin** (`window:pin` in `main/main.js`): the `[data-pin]` buttons, at the bottom right of home and in the player controls (left of fullscreen), toggle `setAlwaysOnTop`. It isn't remembered between launches.
- **Diagnostic log** (`shared/log.js` pure and unit-tested, `main/log.js`, `renderer/log.mjs`): NDJSON, one event per line, in `app.getPath('logs')`. Two 5 MB files rotated by size, not by time, so a fault late in a long film can't push the start of the session out of the file and a crash leaves its evidence behind. The renderer stamps events and ships them to main in batches every 2s (the telemetry sample repeats every 2s per peer, so a write per event would be an IPC message per event); main stamps its own and owns the file. `record` buffers before `start()` opens the file, because a fault during startup is the one worth keeping. **Every line carries both clocks:** the wall clock lines two people's files up against each other, the monotonic clock orders events inside one process, and `clock/offset` records the measured peer offset from `updateClock` so a 2-second control loop can be read across two logs. The load-bearing events are `telemetry/host-sample` and `telemetry/viewer-sample` (every 2s) plus `telemetry/send-quality-change`, which records what `chooseSendQuality` decided and why — that ladder is otherwise invisible from outside, and a viewer cannot tell packet loss from a dipping bandwidth estimate. **Redaction runs in main over every value, not just risky-looking ones,** because the file is meant to be sent to someone else: absolute paths collapse to `…/name.ext` and addresses to `[ip]`, while usernames and room codes are kept because they are the correlation keys. Settings → "Having problems?" writes one combined file through a save dialog and reveals it in the folder; no upload, no server. `npm run test:logging` drives the real IPC surface in Electron and asserts no user paths survive an export.
- `shared/codecs.json`: MediaSource codec strings. The main process uses it for mime types; the renderer uses it to probe `isTypeSupported`.
- `main/turn.js`: optional TURN credentials from an HTTPS broker, with bounded requests, caching and expiry. Packaged `config/turn.json` may contain only `endpoint`; `scripts/check-turn-config.js` rejects bundled secrets. Private user-data `turn.json` may supply static ICE servers. `renderer/network.mjs` renews configuration across friends, rooms and pooled connections. With no configuration, STUN only; `relay/` contains an optional separately deployed broker.

## Verified constraints (don't regress these)

- **Saved-room presence** (`renderer/room-presence.mjs`): Home watches saved codes in `presence:<code>` rooms under the same `APP_ID` as friends and media; active participants watch only their current room. Signed handshakes bind identity to the presence channel, and only peers advertising active membership appear on cards. Observers never join media rooms or count as occupants. Heartbeats expire after 30 seconds; leaving removes names immediately when connected. Channel disposal is serialized before reuse. Presence is live and is not persisted in room history.

- **Connection reuse:** friends, persistent media (`persistent:<code>`) and presence (`presence:<code>`) must retain the same transport `APP_ID`. Separate room IDs isolate their protocols. Changing app IDs disables Trystero's connection reuse and makes room joins depend on discovery even when a friend connection already exists. `npm run test:connections` gates releases on joining, friend discovery and rejoining during a simulated discovery outage; see `docs/connection-regression.md` for the 0.3/0.4 comparison.

- **The rename kept its compatibility anchors.** The app is *Watch With Friends* (GitHub: `onlineslav/watch-with-friends`, titled "Watch With Friends - Synced Media Player"), renamed from *Synced Video Player* after 0.4.3. Three identifiers deliberately still say `synced-video-player`, and changing them breaks existing installs: `build.appId` (`app.syncedvideoplayer`) is how NSIS and electron-updater recognise an install, so a new value would install beside the old app instead of upgrading it; `APP_ID` in `renderer/app.js` and `helloText` in `renderer/friends.mjs` are on the wire, so a new value can't see or connect to anyone on an older build. `main/startup.js` copies the old `%APPDATA%\Synced Video Player` profile into the new one once (`carryOverProfile`, marker file, caches skipped) so identity, friends and saved rooms survive; `scripts/patch-trystero.js` accepts either name's marker so an already-patched `node_modules` isn't patched twice.

- **Entry point is `main/index.js`,** which calls `start()` from `main/main.js`. Electron 44 doesn't set `require.main` to the entry file, so a `require.main === module` check never runs and the app idles with no window.

- **Loop restarts must not look like pauses.** A `<video>` that reaches its end sets `paused` and fires `pause` before `ended`. The host's playing state is `hostPlaying()`, which counts `ended` with loop on as playing; otherwise every loop brings the UI back and viewers see a pause.

- **Only 8-bit video may pass through.** 10-bit HEVC/AV1/VP9 plays locally, but `captureStream` sends WebRTC solid black frames. `copyCodecString` forces a transcode.
- **Stream-copy seeks:** ffmpeg backs input seeks off by ~0.13s for B-frame video and lands on the previous keyframe. `media.js` looks up the keyframe with `ffprobe -read_intervals`, and `plan.js` seeks to keyframe + 0.2s. The MP4 muxer normalizes output timestamps to 0 even with `-copyts`, so the renderer sets `sourceBuffer.timestampOffset = offset`.
- **Burned-in subtitles** need `-copyts` for correct timing. The `subtitles` filter gets a relative filename with the process `cwd` set to the file's folder, which avoids Windows drive-letter colons in the filter graph. The filename is escaped twice (`escapeFilterValue`). Image subtitles (PGS/VobSub) use `overlay` in `-filter_complex`.
- **New `video.src` means new captured tracks.** The host republishes its stream on `loadedmetadata`. Seeks and track changes keep the same MediaSource, so the stream isn't interrupted.
- **Don't send `captureStream()` video.** It samples on a fixed 30fps timer: 24fps films judder and 60fps is halved. `renderer/frames.mjs` forwards presented frames through `MediaStreamTrackGenerator` instead, and `captureStream()` supplies only the audio.
- **`requestVideoFrameCallback` fires ~1/s while the window is minimized.** `frames.mjs` falls back to polling `new VideoFrame(video)`, skipping frames whose timestamp hasn't changed. Frames are re-stamped with wall-clock time because media timestamps jump backwards on seek.
- **Codec:** `app.js` puts H.264 first via `setCodecPreferences` (hardware encode/decode on Mac and Windows; VP8 is software).
- **Connection telemetry** (`renderer/telemetry.mjs`, pure and unit-tested): every 2s each side reads `getStats()`. The viewer grows its receiver `jitterBufferTarget` from 250ms up to 750ms on freezes, packet loss or jitter, and shrinks it after 30s of calm. It reports what it receives to the host through the `telemetry` action; the host includes its own send limits (`qualityLimitationReason`) in `state`. Both feed the top-bar badge. The sidebar's room list (`renderPeople`, `describePeer`) shows every person: ping comes from each peer connection's own stats, and the host relays each viewer's report in `state.viewers` so everyone sees everyone. Names arrive through the `profile` action. Freezes only count after 4s of uninterrupted host playback (`nextSteady`), because pauses, seeks and ffmpeg restarts (the state's `epoch`) stall the stream on purpose.
- **Audio quality:** WebRTC Opus is mono by default. `app.js` patches `setRemoteDescription` to add `stereo=1` and an `x-google-start-bitrate` hint, so video doesn't start blurry. `tuneSenders` raises bitrate caps and scales video above 1080p down.
- **Packaging:** ffmpeg/ffprobe must be in `asarUnpack` (paths are rewritten `app.asar` → `app.asar.unpacked`). `ffprobe-static` ships every platform's binary, so the per-platform `files` excludes in `package.json` matter. Mac builds are ad-hoc signed (`identity: "-"`) and not notarized.

- **Room protocol v2:** `renderer/protocol.mjs` validates incoming data; every handler is scoped to its creating session. Room admission verifies signed identity challenges. All roles retain the winning logical host revision and state sequence; commands and streams reference that revision. Subtitle paths stay local behind opaque catalog IDs. `renderer/sync.mjs` measures monotonic clock offsets and sets per-viewer bitrate/resolution ceilings from loss, freezes and available bandwidth. These policies are automatic, not Settings controls.
- **Integration check:** `npm run test:network` bundles the real renderer with temporary test hooks and local IPC discovery, then connects three hidden Electron windows over WebRTC. It uses disposable profiles and synthetic files, without public discovery or relay traffic. It covers friends, signed room admission, video/audio, subtitles, controls, host changes, image ordering, terminal errors and rejoining. Production bundles include no test hooks.
