# Constraints: connection telemetry and log measurements (don't regress)

Moved word for word from CLAUDE.md on 2026-11-12 so a session doesn't load it every turn. Read before touching `renderer/telemetry.mjs`, `renderer/machine.mjs`, `main/machine.js`, or the `viewer-sample`, `host-sample`, `machine-sample` and `link` log events.

- **Connection telemetry** (`renderer/telemetry.mjs`, pure and unit-tested): every 2s each side reads `getStats()`. The viewer grows its receiver `jitterBufferTarget` from 250ms up to 750ms on freezes, packet loss or jitter, and shrinks it after 30s of calm. It reports what it receives to the host through the `telemetry` action; the host includes its own send limits (`qualityLimitationReason`) in `state`. Both feed the top-bar badge. The sidebar's room list (`renderPeople`, `describePeer`) shows every person: ping comes from each peer connection's own stats, and the host relays each viewer's report in `state.viewers` so everyone sees everyone. Names arrive through the `profile` action. Freezes only count after 4s of uninterrupted host playback (`nextSteady`), because pauses, seeks and ffmpeg restarts (the state's `epoch`) stall the stream on purpose.
- **Log measurements** (M1.2; pure parts in `renderer/telemetry.mjs` `readDetail`/`detailDelta`/`parseOpusFmtp`/`linkFacts`, `renderer/machine.mjs`, `main/machine.js`, `parseProgress` in `main/plan.js`; all unit-tested, and `scripts/check-network.js`'s `checkMeasurements` reads them back out of a real three-window run). They only write to the diagnostic log; nothing acts on them. Every stat is optional (older Chromium, other platforms): an absent one is left out of the line, never `null`/`NaN`, so **absent means unavailable**, and `omitNull` keeps lines small. Keys are short because these lines repeat every 2s. A 2s tick writes, per peer, `host-sample` (host) or `viewer-sample` (viewer), plus **one** `machine-sample` for the whole computer (not per peer: a host with seven viewers would repeat it seven times). Counter deltas are over the 2s since the last reading and are skipped when the ssrc changed or a counter went backwards.
  - `viewer-sample`: `a` audio receive health `{lost, rx (packets), jit (ms), conc, sil (concealed / silent-concealed samples), smp (samples received, to turn those into a ratio), ins, rem (samples inserted/removed for time-stretching), jb (audio jitter-buffer delay ms), lvl (RMS 0-1 from totalAudioEnergy, else audioLevel)}`; `s` A/V sync inputs `{aJb, vJb (jitter-buffer ms per track), aPlay (media-playout delay, audio), aEpt, vEpt, av (= vEpt - aEpt, ms), out, base (the viewer's Web Audio outputLatency/baseLatency, ms: received sound plays through that graph, not the <video>), off (the estimated sound-late offset in ms, `soundLateMs`: what the bench's viewer offset is compared with)}`; `v` decoder cost `{dec (ms per decoded frame), pli, nack, fir (requests this viewer sent), frz, pau (ms frozen/paused)}`; `set`.
  - `host-sample`: `e` encoder cost `{enc (ms per encoded frame), cpu, bw, oth (ms spent quality-limited for that reason), pli, nack, fir (requests received)}`; `set`.
  - `set` on both samples: `{pri: share priority, ab: share audio bitrate, af: 1/0 audio-first}`, so a quality change can be matched to a Settings change.
  - `machine-sample`: `role`; `p` per-process `[cpu% of one core, MB]` for `m` main, `r` renderer, `g` GPU and `o` all others (`[cpu, MB, count]`), from `app.getAppMetrics()`; `free` MB, `bat` (1 on battery), `th` thermal state (macOS only), `lim` OS CPU speed limit % (only after a `speed-limit-change` event); `lt` renderer long tasks since the last sample (`0` none, `{n, ms, max}`, absent = cannot tell); `host` while playing a file: `ff` ffmpeg speed against real time, `ahead` seconds buffered in the MediaSource, `fr` `{n, avg, max, busy}` spacing in ms of the frames `frames.mjs` forwarded (`busy` = presented frames dropped because the previous write was in flight; gaps across a pause or seek are not counted); `cost` ms of main-thread JS the tick spent in its own code (excludes the wait on `getStats`), so the cost of measuring is itself in the log.
  - `link` event (per peer, written when something in it changes, not every tick): `net {p udp/tcp, l/r local/remote candidate type, rp relay protocol, id the candidate pair's id, lf/rf each end's address family (4, 6, `mdns`), nt local network type (wifi/ethernet/vpn, where Chromium says), sw route switches since the connection began}` (the route is the transport's `selectedCandidatePairId`, else the nominated succeeded pair; a new `id` means the route moved, so a blip can be matched to whose end changed; never an address), `venc`/`vdec {impl, hw, codec}`, `opus {local, remote}` `{ch, st stereo, sst sprop-stereo, br maxaveragebitrate, fec useinbandfec, dtx, cbr}` read from the live SDP (re-read only when the streams change and every 30s: each getter copies the whole SDP). The codec mime type is always there; Chromium only names the encoder/decoder implementation and says whether it is hardware (`powerEfficientEncoder/Decoder`) when the page has capture permission, which a plain viewer does not (so `impl`/`hw` are usually absent).
  - `machine/static` (main process, each time a room is entered, so it survives log rotation): GPU feature status table (`app.getGPUFeatureStatus()`), GPU devices (`app.getGPUInfo('basic')`), every display's refresh rate (`hz`) and size, CPU model.
  - **How the numbers reach the sample:** main (`main/machine.js`, started by `app:in-room`) pushes a reading to the window every 2s with `webContents.send('machine:sample')`, a one-way push with no round trip; the renderer keeps the latest and `freshMachine` drops it if older than 6s. `getStats()` is walked once into an array (`Array.from(report.values())`) that `readStats` and `readDetail` both read: walking an `RTCStatsReport` builds a new object per entry on every pass, and the old two-pass code was the bulk of the tick's cost.
  - **ffmpeg speed** comes from ffmpeg's own `-stats` progress line on stderr (`-v error` alone would suppress it): `parseProgress` reads the last whole line and `session:pull` returns `speed` beside each chunk. It is ffmpeg's average since it started, so it drifts toward 1x while the renderer's backpressure holds ffmpeg back; read it together with `ahead`. The failure message uses `lastMessage`, which skips those progress lines.
  - **Measured** (three hidden Electron windows, loopback, 720p24 file with audio): `viewer-sample` about 830 B and `machine-sample` about 315 B per 2s (plus `link` and `machine/static` rarely); main-thread task time per tick 1.0-1.8 ms with the new fields against 4.0-4.2 ms for the old code on the same harness (`MEASURE_BASELINE=1` runs the cost check alone against an older checkout). `estimatedPlayoutTimestamp` is read but this Chromium leaves it undefined in loopback, so `aEpt`/`vEpt`/`av` appear only where it is populated.
