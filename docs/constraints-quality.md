# Constraints: send ceiling, hardware encode, audio quality (don't regress)

Moved word for word from CLAUDE.md on 2026-11-12 so a session doesn't load it every turn. Read before touching `chooseSendQuality`, sender tuning (`tuneSenders`), the encoder choice, or Opus/SDP handling.

- **Send ceiling recovery (M1.7, `chooseSendQuality`):** `npm run bench -- --variant=burst` (10% loss for 4s, clean loopback) cut the ceiling from 7.8 Mbps to 1.7-4.4 Mbps and, at 1080p, the picture to 540p; with three clean reports needed before the first raise it was back at full size 7.6s (median of 3; runs 0.8, 7.6, 10.7) after the burst, and 10.9s after a 30%/3s burst. `RECOVERY_CALM_MS` is now 4000 (two clean reports): 1080p 0.9s (runs 0, 0.9, 8.9), 720p 0.8s, 30%/3s 0.9s (0.9, 0, 2). **The stall memory is deliberate and was left alone:** after trouble the ceiling stays under 85% of the rate that failed for 60s (`SAFE_MEMORY_MS`), so the ceiling itself stands at ~82-87% of its old value at 10s (66% before) and never gets back to it inside 30s; it only shows on content that needs more than that (the bench's testsrc2 needs 7-9 Mbps, a film 3-6). It protects the real Wi-Fi night in `test/sync.test.mjs` where the estimate (7.7-8.9 Mbps) overshot what the link carried (5.9), so a capacity-based exemption would undo it. Freezes after a 10% burst: longest gap between presented frames 267-300ms, no PLI/FIR (NACK retransmission repairs it); at 30% for 3s the gap reaches 550-1134ms because retransmissions are lost too, and Electron 44 has no API to ask for a keyframe sooner.
- **Hardware H.264 encoding (M1.7):** Chromium does not name the encoder (`encoderImplementation` and `powerEfficientEncoder` stay empty without capture permission, so the `link` event's `venc` has only the codec) and `mediaCapabilities.encodingInfo` says `powerEfficient: false` for every codec, so neither proves anything. What does: Windows' `GPU Engine(*engtype_VideoEncode*)Utilization Percentage` counter shows the Electron GPU process using the NVIDIA video-encode engine (up to 12-14%) while the bench film plays and 0 otherwise; `app.getGPUFeatureStatus().video_encode` is `enabled`; and `e.enc` in `host-sample` (encode ms per frame) reads 6.7-7.5ms at 720p60 with no CPU limit. Check it the same way (`Get-Counter` during `npm run bench -- --variant=film --fps=60`) after changing codec preferences.
- **Audio quality (M1.6):** WebRTC's Opus is mono unless the *receiver's* SDP asks for stereo, and the decoder follows the receiver's OWN (local) SDP, so editing only the host's copy of it left every viewer decoding mono (bench: L/R separation 0 at the viewer). The Opus parameters are chosen on purpose in `shared/opus-sdp.mjs` (`preferStereoOpus`): `stereo=1; sprop-stereo=1` (two channels), `useinbandfec=1` (Opus FEC rebuilds a lost packet from the next one), `usedtx=0` (no silence suppression: music and quiet passages keep flowing), `maxplaybackrate=48000` (full band), `maxaveragebitrate=510000` (the format's ceiling; the real cap is the sender's `maxBitrate`); never `cbr`, never `ptime`. It is applied to **every** Opus section of an SDP (a connection that has carried several films has several audio sections), in two places: the remote description in `app.js` (`setRemoteDescription`, which also adds the `x-google-start-bitrate` hint so video doesn't start blurry) and each **local** offer and answer inside Trystero's `peer.mjs` (`scripts/patch-trystero.js`, marker `opus sdp v2`): the argument-less `setLocalDescription()` became create, edit, set, including the ICE-restart offer, with a rollback left alone. Because that is two steps, every description operation in the peer (our offers and answers, remote offers, remote answers) runs one job at a time, each reading the signalling state when its turn comes; a remote offer waits for a local one in flight, then rolls back (a rollback in `stable` throws, which is what a remote offer between `createOffer` and set used to cause). If the edited description is refused the browser's own is used. `test/transport.test.mjs` (a signalling-rule-accurate fake, glare at every timing, ICE restart, refusal) covers the patched dependency; `npm run test:compat` negotiates with a v0.8.0 copy. `parseOpusFmtp` (log line `link`) reads the audio section that carries sound (a track, then not inactive, last wins), not the first. **Congestion ladder (not a loss ladder):** each viewer has its own audio ceiling (`chooseAudioStep` in `sync.mjs`, state `person(id).audio`): the configured cap (`AUDIO_MAX_BITRATE`, or Settings' share bitrate), or a **128 kbps floor** while that viewer's link is congested, one step back up after 30s without congestion. Never lower than 128 kbps, and never triggered by random loss: the bench at 5% random loss measured the same concealment at 64 kbps as at 256 (CELT-mode Opus, which music gets, has no in-band FEC to spend the bits on), and a smaller stream does not make random loss less likely. Congestion means the sender's `qualityLimitationReason === 'bandwidth'` for ~4s (only while the estimate is under 3 Mbps or unknown: with more, the video encoder merely wants more than it needs) or `availableOutgoingBitrate` under 1.5 Mbps for ~10s, neither counting in the first 30s of a connection (the estimate starts near 300 kbps and the encoder reads "bandwidth limited" while it climbs, on any link; the clean-link bench took the step at 2s before this window existed). **It is skipped entirely while "keep audio quality" is on, which is the default**, so by default the audio is always at its configured cap. Logged as `audio-step-change`; `tuneSenders` reads it, and `setParameters` runs once per change (it remembers what it last set per sender, since not every field reads back). **"Keep audio quality"** (`shareSettings.audioFirst`, Settings → Advanced, on by default) means exactly three things: the audio encoding's `priority` and `networkPriority` are set to high (which asks for DSCP marking of its packets, honoured only where the OS and network allow, and tells the encoder it matters), and the ladder above never cuts it. It has no measured effect on how a congested link is split between audio and video: at a 1500 kbps cap the audio got its full 256 kbps with it on or off, and Chromium does not share bandwidth between a connection's audio and video by those priorities without a field trial that Electron does not honour. **One `captureStream()` per element, and sections that go away (M1.11):** every file after the first used to reach viewers with picture and no sound. `publishStream` called `video.captureStream()` again on every `loadedmetadata`; the first capture's listeners survived, took the element's audio copy callback from the second capture and stopped its track. Now `captureElement` captures the host's `<video>` once and keeps it; what is published are `track.clone()`s of the capture's audio (the picture is `frames.mjs`'s generator), and `unpublishStream` stops only the clones and the generator. Chromium does NOT end the capture's old audio track when the source changes: it adds the new file's track and leaves the old one live and silent, one more per file, so the capture's `addtrack` listener stops every audio track before the new one and tells the sink, which retires that clone's sender for 5s and, when the new clone arrives, `replaceTrack`s it onto the same sender (one audio section, the viewer's receiver and track stay, no renegotiation); unclaimed it is released, and a peer whose sender refuses the new clone gets it on a sender of its own (only that peer). Every publish's per-peer promise is checked (`afterPublish`): a failure is logged as `media/publish-failed` (`replace-track-failed` for a refused swap) instead of being swallowed, which is how the glare bug below went unseen. **Sections:** `pc.removeTrack()` leaves the transceiver (with its full codec list) as an m-section nothing reuses, so every film added an audio and a video section for good: ~10 KB of offer per file, over the 64 KiB `@_signal` may be at the 7th film, where the patched receive budget closes the connection to every viewer (a reused connection carries it across rooms). The patched `peer.mjs` (markers `stop transceivers v2` and `v3`) stops transceivers on `removeStream`/`removeTrack` (the section is rejected, then recycled: 5 sections, under 20 KB after 25 files). The rules are in `shared/transceivers.mjs` (`stopSender`, `addSender`; copied beside `peer.mjs` like `opus-sdp.mjs`, and imported by `app.js`), learned the hard way: **stop only once the section was negotiated and the other end does not send on it** (`currentDirection` `sendonly` or `inactive`). A transceiver gets its `mid` from the local offer that first carries it, before any answer; v2 stopped it then, and when that offer was rolled back on glare (the polite end) it was left stopped with no `mid`, in no offer, for good: negotiation "needed" after every round (an Electron probe: 83 `negotiationneeded` in 2s, 280 offers in a 5s run, for as long as the connection lasts), and `addSender`'s idle search did not skip stopped transceivers (setting a stopped one's direction throws). So anything not yet negotiated is only detached (`removeTrack`) and **stays detached**: a first version stopped it once negotiated, and `test:compat`'s new-host-to-0.8.0 glare failed 2 of 6 runs (485a105: 6 of 6), because the old copy's native `addTrack` put its share on that receive-only section in that very window and the later stop rejected it with the share on it (`check-compat.js --host=new --runs=N` prints both ends' descriptions when a glare does not settle). The cost is at most one leftover section per publish taken off within a round trip of being made. `sendrecv`/`recvonly` means the other end sends on it (a copy from before this reuses its receiving transceiver for its own share, as native `addTrack` does; and Chromium hands a detached transceiver to the other end's next section of the same kind, seen in the probe), so it is left detached. `addTrack`/`addStream` make their own transceiver (`addTransceiver`, reusing a detached never-negotiated one, never a stopped one) instead of letting `addTrack` take one of the receiving transceivers the other end made, because stopping our film would otherwise end the share the other end had put on that very section (`test:network` caught this at the first-share step). The signal guard that drops an SDP "without media" (meant for the initial data-channel-only offer) looks for an `m=audio`/`m=video` line instead of `a=rtpmap`; in Electron 44 a real offer that only rejects sections still lists its codecs (and so does its answer), so this only mattered to the fake in `transport.test.mjs`, and older copies accept such offers too. `app.js`'s `stopSendersOf` uses the same `stopSender` for the clones' senders: the room's `removeTrack` cannot, because every room peer is a `shared-peer.mjs` proxy whose `removeTrack` only knows tracks given to it with `addTrack` (`trackOwners`), and these came with `addStream` (`transport.test.mjs` checks this). `unpublishStream` also tells the room to forget each clone (`removeTrack`, for those `trackOwners`). **Known, not fixed (Chromium):** if both ends add a section at the same moment and the two offers give the same `mid` to different kinds (audio on one end, video on the other), the polite end's `setRemoteDescription` after its rollback fails with "RTP extension ID reassignment not supported", whether rollback and set run together or one after another (raw-connection probe); when the colliding new sections match by kind (audio against audio in the probe) it works. Pre-existing and rare (both ends must add media within one round trip), but when it happens the initiator's media does not reach that peer: its offer's resends are refused the same way. A 0.8.0 viewer now sees a receiver track END where it used to see it mute; `test:compat` checks it recovers on the next file. Bench: `--variant=reopen --publishes=10` (files in a row: viewer beep RMS and stereo each time, the host connection's m-sections and offer size); `test:network` opens ten more files on one connection and asserts each is heard, at most 6 transceivers and 6 m-sections (one film is 2, a swap in flight briefly 4), one live audio sender per peer and an offer under 32 KiB (it prints the size: about 8.6 KB, flat), plus a playlist advance. `transport.test.mjs`'s `NegotiatingConnection` (mids, rollback, answers and `negotiationneeded` as Chromium keeps them) covers the glare case: add, offer out, take off, colliding offer, polite rollback, then the next publish, which must settle with no repeated `negotiationneeded`.
