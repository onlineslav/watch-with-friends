# Architecture: benchmark and audio/video sync measurement

Moved word for word from CLAUDE.md on 2026-11-12 so a session doesn't load it every turn. Read before changing the media path, or `scripts/bench*.js`, or anything that touches A/V sync. `npm run bench` is the number every media-path change is checked against.

- **Benchmark options (M1.6):** `--loss N` (percent each way) and `--link-kbps N` damage the link with UDP relays in the main process (`scripts/bench-net.js`; the windows' remote ICE candidates are pointed at them, so real packets are dropped or queued; libwebrtc's own `WebRTC-FakeNetworkSendConfig` field trial was tried and does nothing in Electron 44), `--audio-ladder=off` keeps the audio at its fixed cap for comparison, `--audio-first=off` turns "keep audio quality" off, `--variant=republish` publishes one film three times and reads the viewer's stereo separation after each, `--tree=work/compat/v0.8.1` benches an earlier release (`node scripts/old-tree.js v0.8.1` extracts it with the transport it shipped with, by `git archive`, never linking to this node_modules), `--label=name` names the JSON, `--fps=24|30|60` and `--size=1920x1080` change the clip (the report prints the viewer's frames presented per second, which is what to read at 60fps: rVFC callbacks undercount there), `--variant=loop` (M1.12) loops a 5.5s film `--repeats` times counting the viewer's beeps each time, then a 20s film opened at 17s whose every loop restart goes through ffmpeg (`startAt`; mid-repeat it is moved to 17s with `startAt` again so the start is gone for the next restart, as in a real film), judged by both start beeps, decoded frames and pause samples per repeat, and `--variant=pause` pauses the host 6s at 11s and reads the offset after the resume (see the Web Audio constraint below), `--variant=burst` (M1.7) plays a film, drops `--burst-pct` (10) of the packets for `--burst-s` (4) seconds after `--burst-at` (15) and reads for `--recover-s` (30): seconds until the sender's `scale` is back (the picture size), where the ceiling stands after 10s, the longest gap between presented frames, PLI/FIR/NACK counts and the viewer's freezes (`bench-net.js`'s `setLoss` changes the loss while packets flow). The film variants also print the host's encode time per frame and the hardware evidence described under **Hardware H.264 encoding**. A run that asked for loss and lost no audio packet is invalid; so is one whose sent audio is under the 128 kbps floor at random loss, one that stepped on random loss with "keep audio quality" on, and one on a link under 1.5 Mbps with "keep audio quality" off (`--audio-first=off`) whose audio never stepped. The JSON and printout have the viewer's L/R separation, concealment, audio kbps and, from the sending side's log, the audio steps with seconds since the first receiver report and the number of `setParameters` calls.
- **Benchmark** (`npm run bench`, `scripts/bench.js`, pure parts in `scripts/bench-lib.js` + `test/bench.test.js`): the number every change to the media path is judged by. Same harness as `check-network.js` (hidden-but-shown-off-screen Electron windows, disposable profiles, local discovery, real WebRTC), muted, with the output gain feeding only a tap that reaches the destination through a gain of zero, so nothing is audible. It generates a clip with ffmpeg (moving `testsrc2`, a black patch that turns white for 4 frames, a 1kHz beep starting at the same sample, a quiet bed tone at a different pitch per channel, 28 events at irregular gaps of 2-3.6s, FLAC in Matroska) and measures on the **viewer**: *video time* = `requestVideoFrameCallback`'s `expectedDisplayTime` of the first white frame; *audio time* = the first sample of each beep in an AudioWorklet (`scripts/bench-tap.js`) hung off `output` (after the volume, after `routeRemoteAudio`/`routeTileAudio`), turned into the page's clock with `getOutputTimestamp()` read within 300ms of the beep (the context's clock steps by 10-30ms when the audio service is late, so one line for the whole run is wrong). The gated number is that **viewer absolute offset**, beep heard minus flash shown (positive = sound late), over events after the first 10s of clip; the host's own playback offset, telemetry's `s.off` (the estimate below) and `s.av` are printed beside it and never subtracted. Concealment is `conc - sil` over a window that starts 10s after the picture does. A run is **invalid** (and the bench exits 1) if the viewer's rVFC rate is under 0.9x the clip fps, fewer than 20 steady events paired, or the received beep's RMS is under 0.1. Hooks (`scripts/bench-hooks.js`) are appended to the test bundle only; production code has one seam, `SVP_APP_AUDIO_FAKE` in `main/app-audio.js` (unpackaged builds only). **Share variant:** the sharer's "window" is a canvas drawn on the clip's schedule and sent through a `MediaStreamTrackGenerator` stamped with `performance.now()` (what the Windows composite worker does), and its sound is the clip's own PCM written by `scripts/bench-fake-app-audio.js` through the real `'app'` path (`main/app-audio.js` -> `appaudio:pull` -> `renderer/app-audio.mjs` -> share stream); both ends are tied to one wall-clock epoch, so the bench's ground truth is "painted and delivered at the same instant" (lateness of each is measured and printed; the run is invalid above 5ms p95). **What it does not cover:** real window capture latency, the shared app's own output buffering, and a real device (the muted context reports `outputLatency` 30ms / `baseLatency` 10ms; whether an unmuted device reports the same was not measured because that opens the default output). `--device-latency-ms=N` adds a correction when those read ~0 (`deviceLatencyIncluded: false`). Options: `--variant=film|share`, `--runs=N`, `--count=N` or `--quick` (short clip, not a result), `--share-audio=none` (picture alone), `--share-uptime-s=N` (default 15: the share starts only after both pages are that old, because the audio-timestamp bug below only shows once a page has been up a while; a share started at 5s of uptime hid it), `--raw` (keep every frame and beep in the JSON), `--keep`.
- **Audio in sync with the picture (M1.5):** WebRTC's lip-sync lines the audio and video tracks up by their capture times, so **every track a viewer receives must be stamped on the page's `performance.now()` clock**: `frames.mjs` (film video) already does; `renderer/app-audio.mjs` (the per-app share audio) used to stamp `AudioData` from 0, which put the audio on a base ~the page's uptime away from the video, so lip-sync held the picture back by that amount (~90ms on a fresh page, seconds and rising later) or gave up (`s.av` read ~16000ms at 15s of uptime, with audio and video then playing unsynced). It now uses `createAudioStamper`: the first quantum at `performance.now()` minus the audio that arrived with it, then frame counting, re-anchored after a delivery gap over `GAP_MS` (the Mac helper sends nothing in silence) and nudged towards the clock by at most 2ms per arrival so the helper's clock drift is followed but pull jitter isn't. The Windows whole-app worker (`app-share-worker.mjs`) has its own `performance.now()` that counts from the worker's creation, so it stamps with `pageClockUs` (`performance.timeOrigin` difference, the page sends its origin with `start`; verified in Electron: raw worker reading 508ms vs the page's 3580ms). **Any new generated track needs the same base.** The second gap is the viewer's Web Audio output (`routeRemoteAudio`/`routeTileAudio`, `outputLatency` + `baseLatency`, ~40ms): lip-sync lines the tracks up where audio leaves the jitter buffer, so the sound reached the speakers that much after the picture (film +41-48ms). `applyViewerBuffer` therefore gives the **video receiver** `jitterBufferTarget = adapted buffer + audioPathMs(...)` (`videoTargetMs`) and the audio receiver the adapted buffer alone: one fixed offset added to one side, never the adaptation added twice. Measured: the video wait survives lip-sync (it does not pull the audio later to match). **Captions** use `viewerDelayMs`: a measured delay (the frame's `expectedDisplayTime - captureTime`, or the video jitter buffer's recent delay) already includes the wait; only the requested-buffer fallback has it added (`test/telemetry.test.mjs` walks frames through a cue's start and end for all three sources, with and without the wait). **Telemetry:** `viewer-sample` `s.off` is the estimated sound-late offset in ms (`soundLateMs`: audio jitter buffer + `out` + `base`, minus video jitter buffer + decode, same sign as the bench); it includes whatever lip-sync is holding, so it shows the −650ms share gap that `s.av` (the two tracks' `estimatedPlayoutTimestamp` difference, a capture-time comparison lip-sync has already aligned) read as 11-22ms. `s.av` stays for continuity but do not read a sync problem from it. The estimate is a few ms to ~20ms off the bench's measurement (it cannot see the device or Bluetooth latency).
